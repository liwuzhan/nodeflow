## 0. 结论摘要

本草案支持把口语所称的“节点遗嘱”做成 NodeFlow 的一等声明式契约；正式名称统一使用**节点异常退出安全契约**，避免与现有死亡记录中的 `will`（节点生前 health 证词）混淆。

核心结论如下：

1. **异常退出处置分成两层，不能混为一次共享内存覆盖。**
   - 数据面处置：在生产节点确认死亡后，由 framework 临时接管其输出 buffer，写入声明的安全值或失效态。
   - 资源面处置：PWM、PTO、液压等节点死亡后，由仍存活的安全执行器直接把物理资源置于安全状态。
2. **控制器死亡时应发布被下游明确识别的安全停止命令；只写零速度在存在 bias 等补偿时仍可能不安全。PWM 节点死亡时只改 `pwm_status` 更没有用。** `pwm_status` 是逻辑状态输出，真正的 PWM 动作发生在 Linux sysfs `duty_cycle`。
3. **安全关键输出应显式声明处置策略，但不是每个输出都要伪造一个“安全值”。** 候选策略为 `replace`、`invalidate`、`retain`、`none`；是否扩展为全仓强制待评审。
4. **“先保存案发现场”应解释为在严格字节和时间上限内冻结关键现场，不是等待完整落盘。** 安全动作不能被大 payload、磁盘满、只读文件系统或慢 I/O 阻塞。
5. **framework 接管前必须确认旧 writer 已退出或已被隔离；安全锁存建立前不得让新 incarnation 恢复非零控制。** 否则会破坏当前单写者假设，或让一次安全快照在被消费前就被覆盖。
6. **执行器重启后不得无条件重放历史非零命令。** 防历史重放只是必要条件；底盘是否允许新命令自动恢复，留待评审。
7. **不追求无限递归。** 当前有人监管、低速运行边界下，候选截止线可放在 runtime、OS、驱动层，再由物理急停和现场规程承担其同时失效的剩余风险；该边界必须经边侧验证和安全负责人批准，无人运行不适用。
8. **本文没有批准真实 PWM。** 板型、通道、极性、1.5 ms 的实际 sysfs 值、驱动器失联行为、停车时间和停车距离均须在边侧机和台架上确认。

## 1. 背景、目标与非目标

### 1.1 背景

NodeFlow 的端口采用 latest-value 共享内存：生产者写入最新全量快照，下游读取最新值。这个模型适合低频和中频控制链，但生产者异常退出后，最后一条值会继续留在 buffer 中。

对于状态、地图或日志，保留最后值通常只是“数据陈旧”；对于速度、PTO、转向和执行器命令，最后值可能仍表示“继续运动”。因此，仅仅知道节点已经死亡不够，framework 还需要知道：

- 哪些输出应被替换为安全值；
- 哪些输出应被标记为无效；
- 哪些输出可以保留；
- 哪些硬件资源必须由幸存者直接执行安全动作；
- 安全动作完成后，新节点何时允许恢复控制。

### 1.2 目标

FSC-01：节点异常退出后，在经过评审的时间预算内，使安全关键输出收敛到声明的安全状态。

FSC-02：保存足够的故障现场，同时不让取证阻塞停车或设备回中。

FSC-03：明确区分“写入了安全命令”“设备接口写入成功”和“车辆已经物理停止”三种不同事实。

FSC-04：在崩溃、重启和 buffer 复用之间维持清晰的 writer 所有权，避免 framework 与节点并发写。

FSC-05：让安全策略可在 manifest 和部署配置中审阅、校验、测试和追溯，而不是散落在每个节点的异常分支中。

### 1.3 非目标

本草案不试图：

- 用 Python 保证 runtime、Linux 内核、PWM 驱动和电机控制器同时失效时仍能自动停车；
- 以 `pwm_status`、日志或 sysfs 写成功替代真实的电气波形、轮速或物理停车验证；
- 构建通用分布式事务、复杂 capability 系统或无限层 watchdog；
- 在本轮解决公网攻击模型；当前网络边界仍按农场/仓库受控局域网处理；
- 在 Mac 上推断真实板型、pwmchip、channel、GPIO 权限、PWM 极性或驱动器响应；
- 在多方评审前冻结最终 YAML 字段名、deadline 或硬件安全动作。

### 1.4 首期最小范围

为避免把一次真实问题扩展成通用安全平台，首期候选实现只覆盖：

- 已确认进程退出，不承诺 hang/`SIGSTOP`；
- `track_controller.velocity_cmd` 的明确安全停止语义；
- `drive_pwm.neutral` 一个资源动作；
- 被覆盖端口的有界 preimage 快照；
- drive 资源安全锁存、历史命令阻断和人工 rearm；
- fake sysfs、目标板台架和示波器验收。

通用 `invalidate`、全仓所有输出强制声明、独立 guardian、复杂 handler 注册体系和 hang 检测保留为扩展设计，不进入首期承诺。

## 2. 术语与故障边界

### 2.1 “生前遗嘱”与“异常退出安全契约”

现有死亡记录已经使用 `will` 表示节点最后一次 health 中保存的输入消费位置和年龄，即节点的“生前证词”。本文讨论的是节点死亡后由 framework 执行的安全处置，二者含义不同：

| 名称 | 时间 | 内容 | 用途 |
|---|---|---|---|
| 生前遗嘱 / `will` | 节点活着时 | 最后 health、输入消费位置、输入年龄 | 事故归因 |
| 异常退出安全契约 | 节点不可用后 | 输出替换、失效标记、设备安全动作、重启门禁 | 故障收敛 |

因此，代码字段不建议继续复用 `will`；本文示例暂用 `failure_policy`，最终名称待评审。

### 2.2 关键术语

- **异常退出**：进程已经退出，`process.poll()` 返回退出码。
- **失活或卡死**：进程尚在，但不再产生有效心跳或输出，例如 `SIGSTOP`、死锁或主循环卡住。
- **数据面安全值**：写入输出 buffer 的 schema 合法 payload，例如零线速度和零角速度。
- **失效态**：明确表示数据不可继续使用，不等于用全零伪装成有效测量。
- **资源面安全动作**：直接作用于 PWM、PTO、液压、继电器等设备接口的动作。
- **incarnation**：同一 node id 在同一 run 内的进程世代。
- **fencing**：撤销旧 incarnation 的写权限，并在安全接管完成前阻止新 incarnation 写入。
- **rearm**：故障后重新允许执行器接受运动命令的条件。

### 2.3 故障覆盖矩阵

| 故障 | 本草案的建议覆盖 | 说明 |
|---|---|---|
| 首期纳入的控制/PWM 子节点异常退出、`SIGKILL`，且 runtime/OS 仍存活 | 首期必须覆盖 | 当前只能确认主进程退出；writer fencing 和残余进程组确认属于待实现要求 |
| 节点正常 stop / `SIGTERM` | 复用同一安全动作，但走独立正常停止路径 | 当前 planned stop 不经过 crash handler |
| 节点 `SIGSTOP`、死锁、心跳失效 | 设计预留，需先终止或隔离旧 writer | 不能在旧进程仍可能写时接管 buffer 或设备 |
| 节点启动后立即失败 | 应覆盖已取得资源所有权的部分初始化 | 防止硬件停在中间态 |
| 重启失败、重试耗尽 | 保持安全状态并告警 | 不得恢复旧命令 |
| runtime 进程死亡 | 本契约自身无法执行 | 由独立硬件保护、物理急停和现场规程承接 |
| OS/内核卡死、整机掉电 | 不由本软件契约承诺 | 必须通过硬件和台架验证定义边界 |

首期实现范围建议只承诺“进程已确认退出”的路径；卡死检测和处理可沿用同一契约，但必须另行评审检测依据与 fencing。

## 3. 当前仓库事实

以下仅为 `master@9108b81` 的静态代码事实，不代表边侧硬件已经验证。

### 3.1 Manifest 尚无故障安全字段

- `PortDef` 当前只有名称、类型、描述、buffer 大小和 conflate：[models.py](../edge/runtime/config/models.py#L21-L28)。
- `NodeManifest` 当前只有 entrypoints、inputs、outputs、params、readiness 和 input_watchdog：[models.py](../edge/runtime/config/models.py#L38-L54)。
- YAML parser 只解析这些现有字段：[yaml_parser.py](../edge/runtime/config/yaml_parser.py#L145-L199)。

因此，现在把 `failure_policy` 写入 `node.yaml` 会被静默忽略，不会产生任何安全行为。图实例模型同样没有对应覆盖字段。

### 3.2 NodeMonitor 只在进程退出后进入 crash 流程

NodeMonitor 当前每 1 秒轮询一次进程：[node_monitor.py](../edge/runtime/monitoring/node_monitor.py#L83-L96)。

现有顺序为：

1. `poll()` 发现进程退出；
2. 抢救 stderr，并从 process 字典移除；
3. 记录失败次数；
4. 同步调用 incident recorder；
5. 计算并安排重启。

对应代码见 [node_monitor.py](../edge/runtime/monitoring/node_monitor.py#L98-L188)。当前没有输出安全覆盖或设备 finalizer hook。

### 3.3 现有死亡记录会同步落盘，但不保存正常输出 payload

incident recorder 当前读取冻结 health、统计端口年龄、检查并隔离损坏的输出 buffer，然后追加死亡记录：[main.py](../edge/runtime/main.py#L810-L875)。

在写入安全 payload 前，必须新增对旧 header、seq、write timestamp 和最后 payload 的内存快照；否则覆盖后会丢失最关键的输出现场。完整 incident 持久化不应继续位于安全动作之前。

### 3.4 SharedBuffer 可以承载安全覆盖，但接管条件必须严格

`SharedBufferLite` 是“单写者、多读者”的 mmap latest-value buffer：[shared_buffer_lite.py](../edge/sdk/shared_buffer_lite.py#L55-L78)。

每次写入都会递增 seq，并按 length=0（写入中标记）→ payload → timestamp → seq → length（提交）的顺序写入：[shared_buffer_lite.py](../edge/sdk/shared_buffer_lite.py#L122-L145)。因此，旧 writer 确认死亡后，framework 可以临时写入一条新的安全快照。

但当前锁只保护同一进程内线程，不是跨进程锁。framework 绝不能在生产者仍可能存活时并写。

安全执行器打开完好的现有 buffer 时必须使用 `create=False`。`create=True` 会重写并清零整个文件：[shared_buffer_lite.py](../edge/sdk/shared_buffer_lite.py#L61-L77)。仅当 buffer 不存在，或损坏文件已改名隔离时，才允许按 manifest 大小新建。

### 3.5 PWM 状态输出不等于物理 PWM

PWM 节点唯一输出是 `pwm_status`：[pwm_driver/node.yaml](../edge/nodes/io/pwm_driver/node.yaml#L17-L25)。真正的硬件写入发生在 sysfs `duty_cycle`：[pwm_driver/run.py](../edge/nodes/io/pwm_driver/run.py#L170-L184)。

所以：

- framework 覆盖 `pwm_status` 只能改变观察到的逻辑状态；
- 它不会让 GPIO、PWM 或电机驱动器回中；
- 当前 `pwm_status` 也不是硬件反馈，因为 sysfs 写异常只记录日志，主循环仍可能发布期望状态；
- 没有反馈传感器时，即使 sysfs 写成功，也只能报告“接口写入成功”，不能报告“车辆已停止”。

仓库参数当前声明 50 Hz、中心高电平 1.5 ms，并默认启用极性反转：[pwm_driver/node.yaml](../edge/nodes/io/pwm_driver/node.yaml#L34-L71)、[pwm_driver/node.yaml](../edge/nodes/io/pwm_driver/node.yaml#L105-L108)。代码在反相模式下使用 `duty = period - pulse`：[pwm_driver/run.py](../edge/nodes/io/pwm_driver/run.py#L106-L114)。

这意味着“1.5 ms 高电平”应作为物理语义声明。边侧 handler 需要读取当前 period，使用经台架确认的 `pwm_inverted_polarity` 配置计算 `duty_cycle`，并用实际电气波形复核；不能假定 runtime 能从 sysfs 自动推断极性，也不能在文档中一律写死 `duty_cycle=1500000`。仓库默认参数推导出的数值不是台架证据。

### 3.6 现有 watchdog 是保护层，但不能覆盖 PWM 进程自身死亡

PWM manifest 已为 `velocity_cmd` 声明 0.5 秒输入 watchdog：[pwm_driver/node.yaml](../edge/nodes/io/pwm_driver/node.yaml#L27-L30)。PWM 进程活着时，上游命令断流会触发节点自身回中。

如果 PWM 进程已经死亡、被 `SIGSTOP`、全进程失去调度，或 watchdog 线程本身无法运行，进程内 watchdog 不能执行，只能依靠幸存 runtime 的资源动作、独立 guardian、驱动器硬件超时或物理急停。若只是主循环阻塞而 SDK watchdog 线程仍可调度，它仍可能回中；当前 NodeMonitor 只检测进程退出，尚不能把这种可能性当成统一保证。

### 3.7 重启存在历史命令瞬时重放竞态

完好的输出 buffer 会在节点重启时复用：[port.py](../edge/sdk/port.py#L98-L112)。InputPort 首次连接会同步历史 payload，并优先返回缓存历史。

因此，PWM 节点重启后可能先读取崩溃前的非零速度；现有 0.5 秒 watchdog 能提供缓解，但不能消除“主循环重放旧命令”和“watchdog 回中”之间的瞬时竞态。incarnation 已存在，但当前 InputPort 不用它过滤历史命令。

### 3.8 零线速度和零角速度当前不必然等于 PWM 中位

PWM differential 模式会先把 `angular_velocity_bias` 加到角速度上：[pwm_driver/run.py](../edge/nodes/io/pwm_driver/run.py#L303-L305)。如果现场校准把该值设为非零，单纯的 `{linear_velocity: 0, angular_velocity: 0}` 仍可能产生左右差速。

因此，零速度 payload 必须带有下游明确识别的安全停止语义，并绕过 bias、deadzone 和其他补偿；或者由 drive resource safety executor 直接回中。当前 PWM 节点尚未实现这种 `safety_stop` 语义，不能把示例 YAML 当成已经可用。

## 4. 设计原则

### P1：语义声明与机器绑定分离

本草案倾向由 `node.yaml` 声明“这个端口死亡后应表示什么”“这个资源应进入什么安全状态”，由 graph 或部署配置绑定 pwmchip、channel、极性、设备路径和现场参数。安全态内容由节点/领域负责人给出，runtime 只校验并执行不透明声明，不自行推导业务语义；最终配置位置仍待 DEC-02 裁决。

### P2：安全动作优先，取证不得阻塞

先在有界时间内把现场复制到内存，再执行安全动作，之后持久化 incident。磁盘满、只读或慢 I/O 只能导致取证告警，不能取消安全动作。

### P3：禁止伪造物理事实

写入零速度只说明 framework 提交了安全命令，不代表下游已经消费；写 sysfs 成功只说明设备接口接受了写入。没有下游 ACK、资源安全锁存、轮速、驱动器反馈或其他证据时，不得声称安全值已执行或车辆已经物理停止。

runtime 代写后，buffer write-age 会变新，但逻辑 owner 的 health 仍然是死亡状态。CLI 和下游必须区分逻辑 owner、临时 writer 和节点健康，不能以新鲜 buffer 推导原生产节点已经恢复。

### P4：单 writer 所有权必须可证明

接管前确认旧进程和允许存在的子进程已经退出；接管期间阻止重启；新 incarnation 获得所有权后 framework 不再写。

### P5：动作必须幂等并可分项记录

相同故障事件重复到达时，安全值和设备动作应可重复执行。左右 PWM 等多通道动作必须分别记录成功或失败，单侧失败不能被汇总为“成功”。同一物理资源关联多个 fault 时，动作按资源串行；只要仍有任一 fault 未解除，资源安全锁存就不得 rearm。

### P6：不开放任意 shell 或任意文件写

这不是主要为网络安全，而是为了让语义、权限、参数校验、幂等性、dry-run 和测试结果保持一致。本草案倾向只允许少数 framework 内置并经评审的 handler；最终形式待评审。

### P7：风险在明确的信任边界停止递归

当前有人监管 L0/L1 的长期目标是覆盖安全关键应用节点单故障；首期只覆盖 §1.4 列出的控制/PWM 链。候选截止线是 runtime、OS、内核 PWM、驱动器与物理急停，不为每一层再复制一套完整框架；只有完成边侧验证并由硬件、电气和现场安全负责人签字后，这条截止线才能获批。

## 5. 声明模型

以下 YAML 仅用于表达设计，不是已批准 schema。

### 5.1 数据输出策略

本草案提出四种候选策略：

| 策略 | 行为 | 适用例子 | 约束 |
|---|---|---|---|
| `replace` | framework 写入明确的安全 payload | `velocity_cmd` 写安全停止命令 | payload 必须通过校验，下游必须识别安全停止语义 |
| `invalidate` | 发布 typed 不可用语义 | RTK、pose、硬件逻辑状态 | 下游必须已经定义 invalid 行为；不能借用 buffer 的 length=0 |
| `retain` | 保留最后值，不追加新 seq | 不再参与运行态控制或执行器决策的事实 | 必须说明理由；安全关键命令禁止使用 |
| `none` | 不做数据面动作 | logger、可视化等 | 不得掩盖其资源副作用 |

是否要求所有输出均显式声明仍待 DEC-03 评审。本草案倾向先对安全关键端口强制，普通端口缺失只告警；真实执行器图中，安全关键输出缺失声明应拒绝启动。

### 5.2 控制器示例

`track_controller.velocity_cmd` 的候选声明：

```yaml
failure_policy:
  apply_on:
    - abnormal_exit

  outputs:
    velocity_cmd:
      strategy: replace
      value:
        linear_velocity: 0.0
        angular_velocity: 0.0
        safety_stop: true
        timestamp: "$event.wall_time"
        status: "framework_failsafe"
      completion:
        resource: drive_pwm
        require:
          latch: asserted
          left_action: interface_written
          right_action: interface_written

  deadline_ms: null  # 待边侧停车预算确认；真实输出模式不得保留 null
```

`safety_stop` 和 `$event.wall_time` 都只是候选语义。当前 manifest 的 `control.velocity` 只是字符串类型标签；部分节点虽能在运行期发布 Pydantic metadata，但静态 validator 和 incident 路径并不消费它，而且启动前不可用。因此，正式实现前仍需确定统一的 contract schema 来源。

当前 PWM 节点不识别 `safety_stop`，也不会绕过 `angular_velocity_bias`；这段 YAML 不能直接投入运行。控制器新 incarnation 需要哪些动态输入产生新提交后才可重新发布运动命令，也应按输入端口或控制 edge 单独声明，不能用含义模糊的 node-level `fresh_input` 代替。

`latch: asserted` 只证明“禁止恢复非零输出”的锁存已经建立，不证明物理接口动作成功。左右通道必须分别达到 `interface_written`；若未来有可靠反馈，再把 `feedback_confirmed` 加入更高等级完成门槛。任一通道失败时 fault 和锁存均保持，不能把 completion 记为成功。

### 5.3 非控制输出示例

```yaml
# RTK / pose：不能用 0,0 伪造有效位置
failure_policy:
  outputs:
    pose_enu:
      strategy: invalidate
      reason: "producer_unavailable"

# 可视化：死亡不需要代写业务数据
failure_policy:
  outputs:
    trajectory_image:
      strategy: none
```

如果对应消息类型尚未定义 invalid 语义，则不能只在 YAML 中发明 `invalidate`；应先补齐下游契约，或暂时选择 `none` 并依靠 freshness/watchdog 停止消费。

### 5.4 设备资源动作

PWM 等硬件 sink 需要独立的资源动作：

```yaml
failure_policy:
  apply_on:
    - abnormal_exit

  outputs:
    pwm_status:
      strategy: invalidate
      reason: "producer_unavailable"

  resources:
    drive_pwm:
      action: neutral

  anti_replay:
    velocity_cmd: require_new_commit
  rearm:
    mode: manual_then_fresh  # 草案倾向；待评审
    input: velocity_cmd
  deadline_ms: null
```

`pwm_status: invalidate` 只有在该消息类型和下游已经定义 `interface_state_unknown` 等无效语义后才能启用；它不能携带“已回中”的期望值冒充硬件事实。

机器相关绑定放在 graph 或部署配置。以下示例只映射 owner 参数名，不重复维护另一份数值：

```yaml
safety_resources:
  drive_pwm:
    owner: pwm_driver
    handler: linux_sysfs_pwm_pair
    params_from_owner:
      frequency_hz: pwm_frequency
      neutral_high_pulse_ns: pwm_center_ns
      left_chip: left_pwmchip
      left_channel: left_pwm_channel
      right_chip: right_pwmchip
      right_channel: right_pwm_channel
      inverted_mapping: pwm_inverted_polarity
      dry_run: dry_run_mode
    # 参数值、实际电气极性及 enable 策略必须在边侧机确认
```

首期对 `drive_pwm` 的强制执行点建议明确为：

- **PWM owner 仍活着**（例如 track_controller 死亡）：runtime 断言 drive 锁存；PWM driver 必须在每次硬件写之前检查该锁存，锁存期间只允许写中位并拒绝所有非零命令，同时返回左右通道 action result。
- **PWM owner 已确认死亡**：runtime 在完成进程组 fencing 后临时取得 sysfs 独占权，由 resource safety executor 直接回中。
- 两条路径互斥；resource executor 不得与仍活着的 PWM owner 并发写 sysfs。

资源 handler 至少必须：

1. 使用单一、冻结且可追溯的参数来源；当前 runtime 尚无统一的 resolved 参数对象，这一 resolver 必须实现，或改为由 resource binding 提供完整权威值。节点与 executor 必须引用同一规范化快照和 hash；
2. 无法可靠解析 `dry_run_mode` 时拒绝硬件写；dry-run 时不得触碰 sysfs；
3. 读取并校验当前 period，使用 `pwm_inverted_polarity` 映射计算 `duty_cycle`，再以台架波形确认实际极性；period 不匹配时首期应进入 fault，不能在 enable 状态下临时改频率；
4. 左、右通道分别执行、分别记录结果；
5. 在部分失败时明确返回 fault，不能发布“Motors stopped”；
6. 只报告可证明的层级：planned、attempted、interface-written、feedback-confirmed；
7. 保持幂等；
8. 明确“持续中位”“中位后 disable”或其他动作，最终选择由边侧台架决定。

### 5.5 校验要求

加载 graph 时至少校验：

- 声明的输出端口真实存在；
- 每个安全关键输出都有策略；
- `replace` payload 可序列化且不超过 buffer 容量；
- 动态字段可以解析；
- 有结构化 schema 时必须通过 schema；
- `invalidate` 已有类型级和下游语义；
- `retain` 对安全关键命令无效；
- resource handler 在白名单中；
- resource binding 唯一、参数完整、owner 明确；
- 真实输出模式下 `deadline_ms` 已填写；
- dry-run 不会触发任何真实设备写入。

## 6. 故障处置时序

建议的严格顺序如下：

1. **检测故障**
   对异常退出，以 `poll()!=None` 为依据；对卡死，必须先走单独的不可用确认流程。

2. **冻结身份与所有权**
   标记 `run_id + node_id + dead_incarnation` 已进入处置，阻止重复 handler 和新进程抢先启动。

3. **确认旧 writer 不再运行**
   主进程已退出；若节点允许派生子进程，还需确认或终止残余进程组。

4. **在有界时间内冻结现场**
   始终记录最后 health、stderr 和相关输出的 header、seq、write timestamp；仅复制即将被覆盖的小 payload。候选上限为每端口 256 KiB，并另设总耗时上限；超限时只保留长度和原 run 路径。读取完好 buffer 时只允许 `create=False`。

5. **立即执行安全动作**
   在同一 safety phase 中按预定义顺序写数据面安全值或失效态，并执行相关资源 handler。具体节点只执行与其故障相关的动作，任何动作都不得等待 incident 落盘；NodeMonitor 也不得同步等待无界慢 handler。

6. **记录动作结果**
   incident 中记录每个端口和每个资源动作的开始时间、结束时间、结果、错误、写入 seq 和 deadline 是否满足。

7. **确认传播或保持安全锁存**
   `replace` 写成功只表示安全快照已提交，不表示下游已经消费。执行器链必须由下游安全锁存并明确 ACK，或由资源安全执行器持续保持 safe；锁存解除前，新 incarnation 的非零输出不得恢复物理控制。

8. **持久化有界现场**
   把步骤 4 的有界快照、步骤 6 的结果和步骤 7 的 ACK/锁存状态写入 incident。大 payload 不直接塞入 JSONL；取证失败单独告警，不反向撤销安全动作。

9. **决定是否重启**
   安全锁存建立或资源动作进入明确终态后才能启动新 incarnation。资源动作失败时，进程是否重启与车辆是否重新授权运动必须分开裁决。

10. **执行 anti-replay 与 rearm**
    新节点不得消费启动前缓存的非零命令。对要求新输入的端口，baseline 至少包含 buffer identity/generation、seq 和 write timestamp；同一 generation 内用 uint32 模运算判断新提交。若 buffer 换代，先丢弃重连时的首条历史快照并建立新 generation baseline，再等待下一次提交。通过 anti-replay 后，仍须满足独立的 rearm 策略。

### 6.1 竞态与 fencing

每个故障事件使用 `run_id + node_id + dead_incarnation` 唯一标识。要求：

- 同一事件重复处理不产生额外副作用；
- framework 写安全值前旧 writer 必须已经退出；
- fallback 完成前 restart 不得发生；
- 新 incarnation 建立后 framework 不再写；
- 旧 incarnation 的安全结果不能被归入新 incarnation；
- 对卡死进程，必须先终止或隔离，再进行 buffer 和设备接管；
- 同一物理资源的多个 fault 共用一个锁存和未解除 fault 集合，集合非空时不得 rearm。

进程重新启动或 health ready 不自动等于 fault cleared。每类 fault 必须有独立恢复条件，例如新 incarnation 就绪、配置一致、neutral action 成功且必要输入有效。`fault cleared` 与 `manual rearm` 是两个不同状态转换；只有 fault 集合为空且人工 rearm 完成，才能解除 drive 锁存。

### 6.2 重启与恢复运动

anti-replay 是无条件约束：禁止重放启动前历史 payload。它只解决历史缓存竞态，不等于授权车辆重新运动。

候选 rearm 策略：

| 策略 | 行为 | 风险 |
|---|---|---|
| `automatic_after_fresh_input` | 指定输入出现按 uint32 模运算判定的新提交后自动解除锁存 | 活着的上游可能很快发布新非零命令并自动续跑 |
| `manual_then_fresh` | 人工授权时重新建立 baseline，只接受授权之后的新提交 | 更安全，但会增加现场操作和恢复等待 |
| `manual_resume_latest` | 人工授权后立即采用锁存期间积累的 latest | 可能在授权瞬间立即运动，只能在现场明确接受时使用 |
| `new_run` | 必须重新启动整个 run | 最保守，恢复成本最高 |

本草案对有人监管底盘暂时倾向 `manual_then_fresh`；是否允许 `automatic_after_fresh_input` 或 `manual_resume_latest`，由控制和现场安全评审裁决。无论选哪一种，anti-replay 都必须先通过。

## 7. 组件职责

| 组件 | 应负责 | 不得宣称 |
|---|---|---|
| Manifest/parser/validator | 读取、合并、校验安全契约 | 未解析字段已经生效 |
| NodeMonitor | 检测退出、冻结 incarnation、触发有界处置、控制重启顺序 | 1 秒轮询等于硬实时；无界慢 handler 不会影响安全时限 |
| Incident recorder | 保存有界 preimage、原始现场引用和动作结果 | 取证成功才允许停车；把大 payload 塞入 JSONL |
| Buffer fail-safe writer | 在旧 writer 死亡后写安全 payload | 写 buffer 等于硬件已执行 |
| Resource safety executor | 按获批 handler 操作设备接口、维护资源锁存并分项报告 | sysfs 写成功等于车辆已停止 |
| Restart coordinator | 在 fencing 后启动新 incarnation，执行 rearm | 自动重启等于自动恢复运动 |
| 下游节点 | 尊重 freshness、invalid 和 rearm 语义 | 继续永久使用本地旧缓存 |
| CLI/监控 | 展示 planned/attempted/result/deadline/remaining risk | 将期望状态展示为物理确认状态 |

首期资源 safety executor 可以位于 runtime 内，以控制改造规模。是否拆为独立 guardian 或 systemd helper，是面向无人运行或 runtime 单点故障的后续选择，不作为首期默认。

## 9. 时间预算与安全层级

### 9.1 当前时间事实

- NodeMonitor 当前轮询周期为 1 秒；
- PWM 输入 watchdog 当前为 0.5 秒，但只在其线程仍可调度时有效；
- 本机制不是硬实时系统，仅声明 YAML 值不构成安全保证。

### 9.2 deadline 的来源

`deadline_ms` 必须由以下事实反推：

- 从故障实际发生到物理安全效果的完整端到端时间，而不是从 NodeMonitor 检测到之后才计时；
- 最大批准速度；
- 故障检测最坏延迟；
- buffer fallback 和资源 handler 的最坏执行时间；
- 驱动器响应时间；
- 车辆惯性、地面条件、坡度；
- 允许停车距离和人员安全边界。

Mac/CI 可以验证逻辑顺序并取得初步软件延迟，但不能冻结目标板最坏调度延迟、驱动器响应和物理停车预算。草案和 dry-run 可以保留 `null`；真实输出模式必须由目标板、台架和现场数据冻结 deadline。

### 9.3 风险截止线

当前有人监管 L0/L1 可采用以下边界：

1. 本契约首期目标是由 runtime 的输出处置和设备安全动作覆盖 §1.4 列入范围的安全关键节点单故障；
2. runtime 自身失效是已知剩余风险；
3. 物理急停、现场操作员/安全员以及经验证的驱动器保护承担最后边界。

无人值守，或没有现场人员能在批准时限内实施物理急停的远程运行，不得把 runtime 作为唯一自动停车者；至少需要独立 guardian、驱动器硬件 command-TTL 或等效的独立失效保护，再叠加物理急停。L2 是云边功能分层，不自动等同于无人值守。

## 10. 验证与验收

### 10.1 Mac / CI 可验证内容

以下测试可以在当前开发机或 CI 完成，但不构成硬件验收：

- manifest/parser 能读取并拒绝非法 contract；
- 安全关键端口缺失策略时在真实输出配置下拒绝启动；
- 旧 payload 在覆盖前被内存快照；
- fallback 使用 `create=False` 打开正常 buffer，并产生新 seq；
- 旧 writer 未死亡时拒绝接管；
- incident 目录只读、磁盘满或慢 I/O 时，安全动作仍被调度；
- fake sysfs 左成功/右失败、右成功/左失败、双失败均被分别记录；
- dry-run 绝不触碰 fake/real sysfs 写路径；
- 崩溃后立即重启不会并发双写；
- PWM 重启不会消费启动前历史非零命令；
- buffer quarantine/换代后，重连历史不会被误判为 fresh；
- `manual_then_fresh` 在人工授权时重建 baseline，只接受授权后的新提交；
- resource executor 输入与被杀 incarnation 的冻结参数逐字段一致，缺字段或配置漂移时拒绝执行/恢复；
- 同一故障事件重复执行保持幂等。

### 10.2 边侧机与台架必须验证

| 编号 | 场景 | 预期证据 | Go/No-Go |
|---|---|---|---|
| ACC-01 | 确认板型、pwmchip、channel、左右映射、权限；核对冻结参数快照 | 目标机记录、参数 hash 和逐字段复核表 | executor 参数与被杀 incarnation 不一致即 No-Go |
| ACC-02 | 确认 50 Hz、1.5 ms、极性和实际 `duty_cycle` | 示波器波形 | 不能只看日志或 `pwm_status` |
| ACC-03 | 非零速度时 `kill -9` 控制器；包含非零 `angular_velocity_bias` | buffer seq、安全停止 ACK/锁存、实际 PWM/轮速时间线 | 不得把零 v/w 经补偿变成运动；在批准 deadline 内停车 |
| ACC-04 | runtime/OS 存活时 `kill -9` PWM 子节点 | 两路实际波形进入安全状态 | 任一路残留即 No-Go |
| ACC-05（扩展阶段） | `SIGSTOP` / 死锁 PWM 节点 | 检测、终止/fencing、两路回中时间线 | 首期不承诺；扩展启用前不得与旧 writer 并写 |
| ACC-06 | 左右任一通道写失败 | 两路分项结果及车辆行为 | 不得伪报 stopped |
| ACC-07 | 节点崩溃后立即重启和人工 rearm | 无历史重放；`manual_then_fresh` 仅采用授权后新提交 | 人工授权前运动或授权瞬间采用锁存期 latest 均为 No-Go |
| ACC-08 | runtime 整体被杀 | 驱动器保护或物理急停流程 | 记录为当前风险边界 |
| ACC-09 | 信号线断开、系统掉电、SoC 卡死 | 驱动器和硬件真实行为 | 未知行为不得假定安全 |
| ACC-10 | 最大批准速度、不同地面条件 | 停车时间和停车距离 | 用实测冻结 deadline |
| ACC-11 | 控制器与 PWM 先后故障、先后恢复 | 同一 `drive_pwm` fault 集合和锁存时间线 | 任一 fault 未解除时不得 rearm |
| ACC-12 | 非零 PWM 下 stop-dataflow、runtime shutdown、`SIGTERM` | 双通道回中结果、退出顺序和端到端时间线 | 任一路未回中或超 deadline 即 No-Go |

台架顺序仍应遵循：目标板 dry-run → 电机离地/履带架空 → 空旷区域最低速度 → 受控观察期。

## 11. 迁移、回滚与实施授权

### 11.1 建议迁移阶段

1. **设计评审**：只审字段、责任、风险边界和验证计划，不改运行代码。
2. **解析与静态校验**：支持 contract，但仅展示，不执行。
3. **数据面 dry-run**：在仿真和测试图执行 buffer fallback，不碰硬件。
4. **fake resource handler**：验证顺序、部分失败、幂等、incident 和重启竞态。
5. **目标板 dry-run**：确认 resolved 参数和权限，不使能真实运动。
6. **台架验证**：示波器和架空履带验证。
7. **现场受控启用**：完成多方签字后，才允许最低速度真实输出。

### 11.2 兼容策略

- 迁移期：旧 manifest 缺失 contract 时普通图告警；
- 安全关键图：缺失 contract 或 deadline 时拒绝真实输出；
- 首期目标：所有安全关键输出显式声明 `replace` / `invalidate` / `retain` / `none`；是否扩展到全部输出按 DEC-03 执行；
- 评审通过后，再同步更新节点开发指南和文档索引。

### 11.3 回滚

- 任何实现回滚后，真实车辆配置恢复 `dry_run_mode: true`；
- 已经验证的硬件急停、驱动器保护和现场规程不得随软件回滚移除；
- 回滚不得删除 incident 和失败测试证据；
- 出现无法解释的自动续跑、单侧残留输出或状态伪报，立即回到 No-Go。

在以下角色完成评审前，本文保持“不授权实施”：

- Runtime/SDK 负责人；
- 控制算法负责人；

## 14. 与既有方案的关系

本文是 [WP-A1](NodeFlow_分阶段修复与验收方案_20260901.md#wp-a1执行器安全退出与-pwm-错误透明化) 和既有死亡治理原则的**候选修订案**，不是已经生效的替代方案。

既有原则要求业务安全态由节点负责、framework 不解释 payload。本文保留“语义归节点/领域负责人”，但提出一个受限例外：节点把安全内容显式声明在 manifest 中，runtime 只把已经校验的 literal 当作不透明数据执行，不自行计算业务安全值。若该例外获批，必须回写 2026-08-29 的死亡治理和实施版文档。

原 WP-A1 重点覆盖 PWM 节点自身的正常清理、signal 处理和写失败透明化，并把 `SIGKILL` 列入硬件边界。本文把该边界进一步拆开：

- 控制或 PWM **子节点**被 `SIGKILL`，但 runtime、OS 仍存活：候选由本契约处置；
- runtime 被 `SIGKILL`、OS/SoC 卡死或整机掉电：仍由驱动器保护、物理急停和现场规程承接。

本文相对原方案新增的关键观点是：

- 节点自身无法处理 `SIGKILL` 或解释器暴毙；
- framework 需要声明式处理已经死亡的生产者；
- 数据 buffer fallback 与物理资源 finalizer 必须分开；
- 新 incarnation 恢复前必须有 fencing 和 rearm；
- 取证应先内存冻结，再安全处置，再持久化。

两套机制可以并存：节点正常退出时优先自行进入安全状态；节点来不及执行清理时，由 framework 按本契约执行已声明的异常退出处置。多方评审完成前，两者均不得被描述为已经解决真实车辆安全门禁；若本稿获批，WP-A1 的 `SIGKILL` 验收矩阵也必须同步修订。
