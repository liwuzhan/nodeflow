## 1. 核心任务：增强调试与可观测性 (Debug & Observability)

根据反馈，我们不将繁重的监控逻辑下沉到框架 Runtime 中，而是通过**专用节点**和**工具链**来解决。

### 1.1 开发 "通用调试节点" (`std/debug_sink`)
这是一个特殊的 Sink 节点，用于在开发过程中“旁路”监听数据流。

*   **功能定义**:
    *   **多端口输入**: 支持动态或预定义的多个 `Any` 类型输入端口（如 `in_0`, `in_1`, ...）。
    *   **数据记录**: 将接收到的数据（文本、结构体、二进制摘要）打印到标准输出（Stdout）或日志文件。
    *   **Web 联动 (进阶)**: 内置一个轻量级 WebSocket Server 或 HTTP Client，将采样数据（如 GPRMC 字符串、视频帧的 Base64 缩略图）实时推送给 Web 编辑器前端展示。
*   **应用场景**:
    *   将 GPS 节点的输出同时连给“业务节点”和“调试节点”，在 Web 端实时看经纬度跳变。
    *   查看视频流节点的帧率或抽帧画面。

### 1.2 Web 编辑器调试面板
*   **功能**: 在 Web 编辑器中增加“调试模式”。
*   **实现**: 连接 `std/debug_sink` 提供的 WebSocket，在画布下方弹出一个终端风格的面板，实时滚动显示日志或数据。

## 2. 工具链：CLI 与 AI 辅助调试

开发 `nf` (NodeFlow) 命令行工具，作为连接 Runtime 和 AI 辅助开发的桥梁。

*   **CLI 功能规划**:
    *   `nf start <project_dir>`: 启动 Runtime。
    *   `nf status`: 列出当前所有节点的 PID、状态 (Running/Dead)、最后心跳时间。
    *   `nf logs <node_id>`: 快速查看指定节点的日志（配合 AI 分析报错）。
    *   `nf inspect <node_id>`: 查看节点的输入/输出共享内存状态（高级调试）。
*   **AI 调试流**:
    *   当节点报错时，CLI 可以捕获 Traceback，自动通过 API 发送给 LLM 进行分析，并给出修复建议。

## 3. 硬件与环境适配 (Hardware Adaptation)

为“明天搞个开发板”做准备，确保框架能在 ARM/嵌入式 Linux 环境下流畅运行。

*   **环境验证**:
    *   验证 Python 3.11+ 在目标开发板（如树莓派、Jetson、RK3588）上的运行情况。
    *   验证 `multiprocessing.shared_memory` 在开发板 Linux 内核上的兼容性（通常没问题，但需确认 `/dev/shm` 大小）。
*   **性能基准**:
    *   在开发板上测试 10+ 节点的调度开销。
    *   测试视频流（大块内存）在共享内存中的传输延迟。

## 4. 节点库扩展 (Library Expansion)

随着硬件引入，需要扩展标准库以支持实际外设。

*   **规划中的节点**:
    *   `hw/camera`: 封装 OpenCV 或 V4L2，读取摄像头数据。
    *   `hw/serial`: 封装 `pyserial`，读取串口数据（用于 GPS、传感器）。
    *   `net/rtsp_in`: 读取网络视频流。
    *   `cv/yolo_inference`: (后期) 集成轻量级 YOLO 模型进行目标检测。
