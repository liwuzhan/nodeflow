# 通讯方式变更评审报告（2025-12-24）

## 0. 评审范围

- 文档：`README.md`、`docs/SESSION_SUMMARY_20251224.md`、`docs/ZMQ_HYBRID_IPC_IMPLEMENTATION.md`
- 代码（与“通讯方式/IPC”直接相关）：
  - SDK 数据面：`sdk/port.py`、`sdk/shared_buffer_lite.py`
  - Runtime 编排与注入：`runtime/orchestrator/env_builder.py`、`runtime/orchestrator/startup_coordinator.py`、`runtime/orchestrator/node_launcher.py`
  - 旧 IPC 栈（仍存在于代码库）：`runtime/ipc/*`、`sdk/latest_value_reader.py`
- 目标：核验“通讯方式”在文档中的描述是否符合代码现状，并给出可执行的改进建议。

---

## 1. 执行摘要

### 1.1 结论

- 当前主路径（节点间数据通信）的实现是 **ZeroMQ (IPC 传输) + SharedBufferLite (mmap 持久化最新值)**。
  - 证据：`runtime/orchestrator/env_builder.py:69-98` 注入 `NODE_IN_*`/`NODE_OUT_*` 为 `ipc:///tmp/nodeflow/<node>.<port>`；`sdk/port.py:10-145` 明确采用 `zmq.PUB/SUB` + `SharedBufferLite`。
- `README.md` 中“Unix Domain Socket + MsgPack”的表述与当前主路径实现 **不一致**：
  - 传输层确实是 Unix Domain Socket（ZMQ 的 `ipc://`），但 **序列化并非 MsgPack**：`SharedBufferLite` 使用 JSON（`sdk/shared_buffer_lite.py:12-21,64-79`），ZMQ 通知仅发送序列号字符串（`sdk/port.py:131-134`）。
- 代码库内同时存在两套 IPC 相关实现（混合 ZMQ+BufferLite、以及 runtime/ipc 的 socket/msgpack/shared_buffer 等），存在“文档引用错栈、依赖声明错配、行为预期不一致”的维护风险。

### 1.2 风险等级

- Major：依赖声明与实现不匹配（`pyzmq` 未在根依赖中声明），导致在干净环境中“运行即失败”。
- Major：InputPort “late joiner 可读历史数据”的承诺在实现上未完全落地（首次连接逻辑只同步序列号，不返回历史值）。
- Minor：文档叙述与代码细节（JSON/MsgPack、目录路径、命名）不一致，容易误导排障与二次开发。

## 2. 代码事实（以主路径为准）

### 2.1 Runtime 注入的通讯地址

- 输出端口地址：`ipc:///tmp/nodeflow/<node_id>.<port_name>`
  - `runtime/orchestrator/env_builder.py:82-99`
- 输入端口地址：`ipc:///tmp/nodeflow/<from_node>.<from_port>`
  - `runtime/orchestrator/env_builder.py:62-74`
- 启动顺序按拓扑分层，并显式声明“Using ZeroMQ IPC for inter-node communication”
  - `runtime/orchestrator/startup_coordinator.py:33-90`

### 2.2 SDK 端口的真实数据路径

- OutputPort：写共享缓冲区（JSON）→ 发 ZMQ 通知（序列号）
  - `sdk/port.py:83-145`
  - `sdk/shared_buffer_lite.py:17-21,64-81`
- InputPort：接收 ZMQ 通知 / 轮询序列号 → 从共享缓冲区读取 JSON
  - `sdk/port.py:298-345`

## 3. 文档一致性核验（与“通讯方式变更”直接相关）

### 3.1 `docs/SESSION_SUMMARY_20251224.md`

- 结论：总体方向与代码一致（混合 IPC：SharedBufferLite + ZeroMQ；通过环境变量传递 `NODE_OUT_*_BUFFER_SIZE` 等）。
- 需修正/补强点：
  - 文档定位为“支持大数据量传感器”，但当前 SharedBufferLite 序列化为 JSON（`sdk/shared_buffer_lite.py:12,65`），对 numpy/bytes/大数组并不友好，且性能与体积不匹配“高性能”叙述。
  - 文档宣称 conflate=false 预留队列模式，但当前实现对 `conflate` 仅做读取与日志输出（`sdk/port.py:69-75`），行为上仍是“单值覆盖”。

### 3.2 `README.md`

- 结论：对“通讯方式”的表述与主路径实现存在偏差。
- 具体不一致：
  - README 声称“Unix Domain Socket + MsgPack”（`README.md:16-18`），但当前数据落盘采用 JSON（`sdk/shared_buffer_lite.py:12-21,64-79`），ZMQ 通知仅发送序列号字符串（`sdk/port.py:131-134`）。
  - README 依赖列表指向 `requirements.txt`，但根依赖当前未声明 `pyzmq`（`requirements.txt:1-11`），而 `sdk/port.py:11` 直接 `import zmq`。

### 3.3 `docs/ZMQ_HYBRID_IPC_IMPLEMENTATION.md`

- 结论：该文档与代码方向一致（混合架构），但其“数据格式为 JSON/最大 64KB”等描述已经与最新实现出现偏差：
  - SharedBufferLite 默认 1MB（`sdk/shared_buffer_lite.py:26`），且通过 env 可配置（`runtime/orchestrator/env_builder.py:91-97`、`sdk/port.py:69-75`）。

## 4. 主要问题（按严重级别）

### Major 1：依赖声明与实现不匹配（`pyzmq`）

- 现象：SDK 端口实现依赖 `zmq`（`sdk/port.py:11`），但根 `requirements.txt` 未包含 `pyzmq`（`requirements.txt:1-11`）。
- 影响：在“仅按 README 执行 `pip install -r requirements.txt`”的环境里，节点运行将直接 ImportError。
- 建议：将 `pyzmq` 明确加入依赖，或在 README/安装脚本中明确额外安装步骤。

### Major 2：Late-Joiner 语义在实现上未完全兑现

- 现象：InputPort 注释宣称“首次连接：尝试从buffer读取历史数据”，但实际代码只是把 `last_sequence` 同步到当前序列号（`sdk/port.py:289-292`），并未返回历史值。
- 影响：
  - 如果下游节点“晚启动且上游只发送一次”，下游首次 `recv_latest()` 很可能读不到已存在的最新值（没有通知、且 `current_seq == last_sequence`）。
  - 这与 `docs/SESSION_SUMMARY_20251224.md` 及混合架构目标（解决 slow joiner）存在语义差距。
- 建议：将“首次连接的历史值交付”作为验收标准补充到测试与文档口径（不在本次改动范围内，仅建议）。

### Major 3：序列化策略与“高性能/大数据”定位存在偏差

- 现状：SharedBufferLite 使用 JSON（`sdk/shared_buffer_lite.py:12,65,105`）。
- 风险：
  - JSON 对二进制/大数组支持弱，体积与 CPU 开销偏高。
  - README/SESSION_SUMMARY 把场景扩展到激光雷达/相机，容易在落地阶段遭遇序列化失败或性能瓶颈。
- 建议：如果目标确实是大数据，统一主数据面序列化为 MsgPack（代码库已存在 MsgPack 协议实现：`runtime/ipc/protocol.py:17-70`；也有 MsgPack mmap buffer：`runtime/ipc/shared_buffer.py:6-10,111-114`），并明确“允许的数据类型集合”。

### Minor 1：同仓库存在两套 IPC 栈，导致认知与维护成本上升

- 现状：
  - 新栈（主路径）：`sdk/port.py`（ZMQ+SharedBufferLite）+ `runtime/orchestrator/env_builder.py`（ZMQ 地址注入）。
  - 旧栈（仍存在）：`runtime/ipc/channel.py`（socket）、`runtime/ipc/protocol.py`（MsgPack + length prefix）、`runtime/ipc/shared_buffer.py`（MsgPack mmap）、`sdk/latest_value_reader.py` 等。
  - Runtime 仍初始化 `SocketManager`（`runtime/main.py:136-140`），但 NodeLauncher 注释说明“Shared Buffer版本：不再需要socket_manager”（`runtime/orchestrator/node_launcher.py:76-79`）。
- 影响：
  - 文档、测试、工具可能引用不同栈，形成“改了 A 但线上跑的是 B”的错配。
  - 新成员会被 `runtime/ipc/*` 与 `sdk/port.py` 的双实现误导。
- 建议：明确标注旧栈的状态（deprecated/legacy），并在文档中只描述一个“当前默认栈”。

## 5. 建议的对齐动作（不改代码，仅给建议）

### P0（阻断类）

- 明确依赖：把 `pyzmq` 纳入安装口径（`requirements.txt` 或安装脚本），并在 README 的“验证安装/测试”章节覆盖 ZMQ 依赖可用性。

### P1（正确性与承诺一致）

- 增加“late joiner 首次读取历史值”的可重复用例（建议放在 `tests/integration/`），并在文档中把“解决 slow joiner”的验收条件写清楚。

### P2（性能与可扩展）

- 统一序列化策略：若目标是大数据与类型丰富，优先选择 MsgPack，并对 dict/list/bytes/numpy 的策略做清晰定义。
- 统一命名与目录：ZMQ IPC 端点（`/tmp/nodeflow/`）、buffer 文件（`/tmp/nodeflow/buffers/`）、旧 buffer（`/tmp/nodeflow_buffers/`）建议收敛，否则清理与权限策略会越来越复杂。
