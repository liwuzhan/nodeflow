## 0. 本计划的定位

本计划是《Cordis 架构调研报告》经过逐项核实与边界重评之后的**可执行子集**，并叠加本次讨论确立的设计原则。核心判断：

1. NodeFlow 的骨架（进程隔离 + 显式契约 + latest-value mmap + 健康心跳）与项目初衷（降低模型心智负担、支持模型维护机体）**同构**，不需要架构级改造；
2. Cordis 的核心机制（可逆 effect、响应式依赖、进程内热插拔）解决的是「选择单进程」的代价，NodeFlow 选择了进程边界，因此**没有这个代价，也不需要这套机制**；
3. 真正欠缺的是三件小事：**事实可读**（框架自己的账本说得出口）、**状态不自腐**（会话内的重启事件不制造静默故障）、**数据有时间戳**（框架观测的写入时刻）。三者收敛为一件交付物：**死亡记录（验尸报告）**。

预算约束：全部改动合计**约 600–900 行**，分三个波次，无一个新子系统。

## 1. 设计原则（评审基准）

以下原则来自 2026-08-29 讨论，作为评审时判断各项改动是否越界的标尺：

| # | 原则 | 含义 |
|---|---|---|
| P1 | **责任跟幸存者走** | 任何责任必须交给在对应故障发生时仍活着的实体。节点死亡后的处理归框架；框架死亡后的处理归模型（模型在框架之外，是唯一幸存者） |
| P2 | **节点的本分是"病了就大声死"** | 节点最清楚自己是否卡死（输入断流、设备僵住），其职责是进入安全态并显式退出；复活归框架。pwm_driver 的 `command_timeout` 是该模式的原型 |
| P3 | **框架 = 协议** | node.yaml 是 IDL，buffer 命名是寻址，latest-value+seq 是语义。协议演进靠版本化，不靠重写 speaker。模型的主接口是稳定的小工具（CLI），**裸读 mmap 只能作为逃生通道**——否则二进制布局永久变成公开 API |
| P4 | **模型在环 vs 无人值守的分界** | 模型在环时，"反应式"放在模型↔框架边界上，框架只需诚实；框架自主持有安全策略（租约、能力联动）的前置条件是**没有任何智能在环** |
| P5 | **证据按衰减速率分类保存** | 证词（活体状态）随死即逝；遗言（退出码/stderr/死前端口年龄）不可再生；现场（冻结 buffer）体积大且无时间戳则无证明力；档案（run_id/配置/版本）决定物证的意义。**值得长久保存的是验尸报告，不是现场本身** |

监督格（三条边，本计划补齐第三条边的接口）：

```
框架 ──(NodeMonitor 拉起+验尸)──→ 节点        已有/本计划加固
节点 ──(SDK 父进程检测)──→ 框架              已有
模型 ──(status / 死亡记录 / 探针)──→ 框架     本计划补齐
```

### 2.1 真实存在的问题（证据）

| # | 问题 | 证据位置 |

### 2.2 时间戳现状（**修正讨论中的口头结论**）

讨论中曾说"rtk_driver 没有时间戳"，核实后**不准确**，修正如下：

- **payload 层**：主链大部分有 timestamp，但**来源语义逐跳漂移**：
  - `rtk_fix`：NMEA 设备时间，本地墙钟回退（`sensing/rtk_driver/run.py:361`，`nmea_parser.py:118,200`）；
  - `filtered_rtk`：`out["timestamp"] = now`——**本地墙钟覆盖了设备时间**（`sensing/rtk_filter/atom.py:59`）；
  - `pose_enu`：`rtk_data.get('timestamp', time.time())`——实际继承上跳的墙钟（`localization/coord_transform/atom.py:43`）；
  - `velocity_cmd`、`pwm` 侧：有（`control/track_controller/atom.py`、`io/pwm_driver/atom.py`）；
  - `waypoint_selector.atom` / `path_progress.atom` 内部构造的 payload 无。
- **框架层**：完全没有。header 无写入时刻，SDK `send()` 不盖戳（唯一例外：health buffer，`nodeflow_sdk.py:323`）。

**结论不变但更精确**：缺的不是"节点没写时间戳"，而是**框架观测的写入时刻**这一层——它不依赖节点自觉、语义统一、能回答"这个 buffer 上次写入是几时"（payload 时间戳回答不了：生产者可用旧值重发获得假新鲜 ts）。同时设备时间在 rtk_filter 处被墙钟覆盖，属于顺手可修的语义混乱。

### 2.3 已经存在、直接复用的资产

健康心跳（`{node_id}.health`，2s，`nodeflow_sdk.py:215-217`）、CLI stale 判定（3× 间隔）与 IDLE 静态输出识别（`tools/cli/commands/health_cmd.py:311-334`）、启动层内回滚 + 取消 + 测试（`startup_coordinator.py:151-157`、`tests/unit/test_startup_coordinator.py:80`）、崩溃 stderr 抢救（`node_monitor.py:134-139`）、daemon 控制通道（`runtime.control`，`main.py:678`）、preflight（`tools/preflight_runtime.py`）、pwm_driver 安全超时（P2 原型）、`buffer list/inspect` CLI。

## 3. 改造清单

### 波次 W1：无协议变更的修复（先行，约 200 行）

#### W1-1 监控线程异常保护
- **现状**：F-1。
- **修改**：`_monitor_loop` 循环体包 `try/except Exception: logger.exception(...); continue`，保证监控线程不死。
- **规模**：~10 行 + 1 个注入异常的测试。
- **验收**：向监控注入连续异常，节点崩溃仍被检测和重启。

#### W1-2 重启失败进入重试调度
- **现状**：F-2。
- **修改**：`_execute_restart` 回调失败/返回 None 时调用 `retry_tracker.record_failure()`，`can_retry()` 则按退避重新入 `_pending_restarts`；耗尽则维持现有 give-up 日志。重启尝试与节点崩溃共享 `max_retries` 预算，防止无限循环。
- **规模**：~15 行 + 测试。
- **验收**：回调连续失败 N 次后节点进入 give-up，而非首次失败即永久离线。

#### W1-3 CLI 后台启动改状态轮询
- **现状**：F-3。
- **修改**：`sleep(2)` → 每 0.25s 轮询 `is_runtime_running()`，上限 10s，提前成功；超时报错并提示 `tail /tmp/nodeflow_runtime.log`。
- **规模**：~15 行。
- **验收**：模拟慢启动（延迟 5s），CLI 在第 5s 左右返回 success 而非误报失败。

#### W1-4 工程一致性收口（对应 Cordis 报告 M0，全部采纳）
- CI 触发分支加入 `master` 与 `refactor/consolidate-post-ai-review`（合并策略定案后收敛为实际默认分支）；
- `python_requires` 与 README 统一为 3.12+；
- 修正 README 第 228/680 行 ZeroMQ 残留描述、项目树旧路径、`startup_coordinator.py` docstring 与日志中的 ZeroMQ 表述；
- CI 增加 `pytest tests/unit --collect-only` 作为最低门槛。
- **规模**：~40 行（多为文档）。

#### W1-5 `nodeflow status --json` 聚合命令（v1）
- **现状**：模型需要 4 次调用（buffer list / inspect / health / 前述）+ 读日志才能拼出全貌。
- **修改**：新增 CLI 命令，聚合：run 信息（PID 文件 + 图配置）、每节点状态（monitor + health 新鲜度）、每输出端口 seq 与写入情况、按边推导的输入端口连通性、最近一次死亡记录摘要。人读输出为表格，`--json` 供模型。数据来源全部为现有原语，daemon 模式经 `runtime.control` 查询活体；非 daemon 场景回退读文件工件。
- **规模**：~150-200 行（新文件 `tools/cli/commands/status_cmd.py`）。
- **验收**：模型仅凭此一条命令可回答"哪些节点在跑、哪些输入断流、数据多旧、最近谁死过"，不读日志文件。

### 波次 W2：协议 v2——时间与身份（约 350–450 行，一次协调升级）

#### W2-1 Buffer header v2：写入时刻
- **现状**：F-6。
- **布局**：`[seq:4][length:4][write_ts_ns:8]`，`HEADER_SIZE 8→16`；`write_ts_ns` 为 `CLOCK_MONOTONIC`（Linux/macOS 均为系统级 boot 基准，同机跨进程可比）。
- **写序**（沿用 tombstone 语义）：`length=0 → payload → ts → seq → length`；读端一致性检查由"比较 8 字节"扩为"比较 16 字节"（`read_with_sequence` 现有逻辑自然延伸）。
- **SDK 接口**：`InputPort.last_write_age_ms()`；`recv_latest()` 签名不变。
- **兼容**：HEADER_SIZE 为编译期常量，需 runtime 与全部节点同版本升级（单机部署，随一次整图重启完成；buffer 本就在新 run 清场，无混读窗口）。同步更新 `test_shared_buffer_lite.py`、`test_port.py` 对布局的断言。
- **规模**：~60 行 + 测试更新。
- **验收**：任一端口可查写入年龄，误差 <5ms；并发读写压力下无撕裂读（复用现有 seqlock 测试扩展）。

#### W2-2 run_id：运行身份
- **现状**：跨 run 的 buffer、日志、死亡记录无法归因（讨论原则 P5"档案"缺失）。
- **修改**：`start_dataflow` 生成 UUID `run_id`；PID 文件升级为 JSON `{pid, run_id, started_at, graph_id}`（现为两行文本，`main.py:809-816`）；`run_id` 经环境变量 `NODEFLOW_RUN_ID` 注入节点并进入结构化日志前缀；资源路径改为 `/tmp/nodeflow/<run_id>/buffers`（`constants.py` 动态化，CLI 经 PID 文件定位当前 run 目录）。
- **规模**：~80 行（含 CLI 适配）。
- **验收**：连续两轮 run 的 buffer 目录、日志、死亡记录可按 run_id 区分；`status --json` 顶层携带 run_id。

#### W2-3 InputPort 自愈与世代重同步（对应 Cordis 报告 M1，采纳）
- **现状**：F-5；以及生产者重建 buffer 后 seq 语义失效无恢复路径（v2 审查"量产前 P1"）。
- **修改**：
  - 状态机 `DISCONNECTED → CONNECTED`（STALE 留待后续）：`recv_latest()` 发现 buffer 为 None 时按退避（0.2s 起、上限 2s）重试打开；
  - 重同步触发条件：seq 大幅回跳、`write_ts` 倒退、或 buffer 文件 inode/尺寸变化 → 重开 mmap、`last_sequence` 重置为当前值、内部 `generation += 1`、INFO 日志；
  - `get_stats()` 暴露 `{state, source_write_age_ms, generation}`；SDK `report_health` 增加各输入端口摘要（名 → 连通/写入年龄），供 status 与死亡记录消费。
- **规模**：~120 行 + 测试（含"生产者中途重建 buffer"回归用例）。
- **验收**：运行中重启任一上游节点，下游在 2 个轮询周期内恢复收数；全程无永久断流。

#### W2-4 死亡记录（验尸报告）——本计划的核心交付物
- **现状**：F-6、F-7：死亡的全部痕迹 = 日志一行 + 计数器；且载体在 /tmp，关机即失。
- **记录**（JSONL，每次死亡一条，由 NodeMonitor——幸存目击者——在 `_handle_node_crash` 追加）：

```json
{
  "ts_wall": "...", "run_id": "...", "node_id": "rtk_sensor",
  "package": "sensing/rtk_driver", "incarnation": 3, "retry_count": 2,
  "exit_code": 1, "signal": null,
  "stderr_tail": "…≤500 字…",
  "output_ages_ms": {"rtk_fix": 41200},
  "input_ages_ms": {"serial_raw": 41000}
}
```

  - `output_ages_ms` / `input_ages_ms` 由框架事后读该节点输出 buffer 与（按边推导的）输入 buffer 的 header 计算——**回答"死时是上游饿死还是自己卡死"**，依赖 W2-1；
  - **存储位置（关键决策）：持久目录**（默认 `<repo>/var/incidents/deaths.jsonl`，可经 `NODEFLOW_INCIDENT_DIR` 覆盖）。不放 /tmp——农机每日关机，故障上报必须活过断电。buffer 现场（易腐、大体积）留在 /tmp 是正确的，验尸报告必须持久；
  - 保留策略：滚动保留最近 1000 条或 30 天。
- **规模**：~80 行 + 测试。
- **验收**：强杀任一节点 → 记录完整落盘、年龄字段与真实值一致；重启框架/整机后记录仍在；`status --json` 能引用最近记录。

#### W2-5 启动等待改 readiness 驱动（对应 Cordis 报告 M5 缩减版）
- **现状**：F-4。
- **修改**：`node.yaml` 可选 `readiness: heartbeat | first_output`（默认 `heartbeat`）；`_wait_for_layer` 每 0.1s 轮询：心跳模式 = `{node_id}.health` 存在且新鲜；first_output 模式 = 全部输出 buffer `seq>0`；进程退出检查保留（立即失败）。`startup_timeout` 语义改为 readiness 上限（默认 10s），超时**告警并放行**（保持与现状同等的宽容度，不引入新失败模式）；层间延迟 1s → 0.1s（ZMQ 已移除，无订阅建立问题）。
- **规模**：~80 行 + 测试。
- **验收**：`planning_with_real_rtk` 图（11 节点）启动时间从约 `2s×层+1s×(层-1)` 降为 ≈ 最慢节点首心跳 + 余量，实测记录前后值。

### 波次 W3：打磨与约定（约 100–150 行，可拆散）

#### W3-1 设备时间透传修正
- `rtk_filter` 不再用本地墙钟覆盖上游设备时间（`atom.py:59`），仅在缺失时回退并标记 `timestamp_source: "local"|"device"`——修复 2.2 节"语义逐跳漂移"，使"写入仍在继续但设备时间没走"这类失效可被探测。
- **规模**：~10 行。

#### W3-2 清场政策
- `_clean_buffers` 清场前，若上一 run 存在死亡记录：将各端口最后 payload 快照入 `var/incidents/<run_id>/scene/`（单端口 >256KB 跳过，图像类不入），随后再清；
- 保留最近 5 个 run 的 /tmp 目录与快照，超限剪除（F-8）。
- **规模**：~50 行。

#### W3-3 节点输入看门狗约定（P2 原则的 SDK 化）
- manifest 可选参数 `input_watchdog: {<port>: <timeout_s>}`；SDK 在超时后调用节点声明的 `on_input_lost`（默认行为：记录 + 退出，交给框架复活）。pwm_driver 迁移到此约定作为首个用户。**opt-in，不强制存量节点**。
- **规模**：~60 行（SDK）+ pwm_driver 适配。

#### W3-4 stdout 日志降级
- 轮转规格 1GB×30 → 64MB×3/端口（F-10）；崩溃 stderr 的证据价值已由 W2-4 承接。
- **规模**：2 行。

## 4. 明确不做（登记触发条件，防范围回涨）

## 5. 验收标准（汇总）

**可靠性**
1. 向监控线程注入异常 → 线程存活，崩溃检测不中断（W1-1）；
2. 重启回调连续失败 → 进入退避重试直至预算耗尽，非首败即弃（W1-2）；
3. 运行中强杀任一上游节点 → 下游 ≤2 轮询周期恢复；强杀带输出节点 → 死亡记录落盘且字段完整（W2-3/4）；
4. 整机断电重启 → 死亡记录与场景快照仍在（W2-4/W3-2）；
5. 多轮 start/stop 循环后，fd/线程/buffer 文件数回到基线（回归 `test_multi_loop.py` 扩展）。

**事实可读**
6. `status --json` 单命令回答：在跑节点、各输入连通性与数据年龄、最近死亡摘要（W1-5）；
7. 任一端口写入年龄可查且误差 <5ms（W2-1）；
8. 两次 run 的工件可按 run_id 区分（W2-2）。

**性能**
9. 典型图启动时间实测对比：固定等待 → readiness 驱动，记录数值（W2-5）；
10. write_ts 增量成本：20Hz 小包写入路径基准对比，确认无显著回退（W2-1）。

## 7. 待评审问题（请交叉评审模型重点裁决）

| # | 问题 | 当前倾向 | 备选 |
|---|---|---|---|
| Q1 | write_ts 放 header（v2）还是 payload envelope？ | header：零每消息编码成本、语义统一、单机协调升级无兼容窗口 | envelope：不动二进制布局，但每消息付出 msgpack 编码、且依赖节点自觉 |
| Q2 | readiness 默认信号：首心跳 vs 首输出？ | 首心跳（普适、已有基础设施）；first_output 供关键生产者 opt-in | 首输出更接近业务就绪，但静态输出节点需特判 |
| Q3 | readiness 超时策略：告警放行 vs 失败中止？ | 告警放行（与现状宽容度一致，不引入新失败模式） | 严格失败更符合"readiness 契约"，但慢设备（RTK 冷启动）会被误杀 |
| Q4 | 死亡记录位置：`<repo>/var/incidents` vs 独立数据目录 vs 上送云端？ | 仓库内 var/（简单、随代码备份；农机单机） | 上送云端与任务系统联动（依赖 cloud 边界启用，当前不在上机范围） |
| Q5 | `clean_buffers` 默认值是否翻转为"保留+快照"？ | 翻转（证据优先），`--no-clean` 语义反转需同步 CLI 与文档 | 保持默认清场、快照 opt-in（更保守，但默认路径仍毁现场） |
| Q6 | W3-3 输入看门狗默认动作：大声死 vs 输出安全值后继续？ | 默认大声死（P2 原则），安全值输出留给节点自定义回调 | 安全值继续对可视化类节点更友好 |
| Q7 | header v2 的 16 字节一致性检查在非对齐 mmap 上的开销？ | 预期可忽略，需在目标工控机基准确认（验收 #10） | 若显著，退回 envelope 方案（Q1 备选） |

## 8. 附录：对 Cordis 报告（2026-08-28 版）的采纳结论

| 报告条目 | 结论 | 对应本计划 |
|---|---|---|
| M0 一致性收口 | **全部采纳** | W1-4 |
| M1 InputPort 重连状态机 | **采纳**（STALE 态延后） | W2-3 |
| M2 NodeFiber/effect 栈 | 不采纳为机制；真实需求（资源收口、幂等停止）由现有回滚 + W1-1/2 覆盖 | W1-1, W1-2 |
| M3 Capability Registry | 不采纳，登记触发条件 | §4 |
| M4 envelope | **缩减采纳**：仅框架写入时刻进 header；scope/producer/schema 字段不做 | W2-1, W2-2 |
| M5 readiness/健康状态机 | **缩减采纳**：两态 readiness + 告警放行；八状态机与 fail-closed 联动不做 | W2-5 |
| M6 边侧 Reconciler | 不采纳，登记触发条件 | §4 |
| M7 三层 Scope 身份 | **最小采纳**：仅 run_id；三层模型不做 | W2-2 |
| M8 事件总线+不变量注册表 | 不采纳；其诊断诉求由 status 聚合 + 死亡记录以 1/20 成本满足 | W1-5, W2-4 |
