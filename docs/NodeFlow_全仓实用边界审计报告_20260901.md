> 审阅日期：2026-09-01  
> 审阅基线：`master` @ `9108b81`

> 适用边界：低速履带式农用车辆、有人现场监管、物理急停、农场/仓库专用局域网  
> 验证方式：跨模块静态审阅、隔离故障复现、分层测试、真实软件栈 preflight、NodeFlow CLI 空闲态诊断

## 0. 结论摘要

本轮复核后的结论不是“仓库整体不可用”，也不是“测试全绿即可上车”，而是：

1. **Runtime、SDK 与主控制链已经具备可继续迭代的工程基础。** 位姿/目标 freshness、原地转向超时、PWM 存活期间的命令超时、RTK 位置质量过滤、run 级 buffer 隔离等机制已经存在，2026-08-29 的 W1～W3 改造也确实关闭了若干旧问题。
2. **有人监管的 L0/L1 dry-run 与仿真联调可以继续。** 当前真机配置仍为 `dry_run_mode: true`，且现场计划要求物理急停、最少两人、分阶段提速。
3. **解除 dry-run 前仍有三项直接门禁。** 它们分别是：进程退出时 PWM 不保证回中、双通道 PWM 部分写失败被伪装成成功、双天线航向可永久陈旧。若允许作业中热更新地块或计划，规划更新丢失是第四项条件门禁；若现场强制停车并重启任务，可以暂时用流程规避。
4. **L2 云边任务闭环当前不能视为可用。** 动态地块目录、run-scoped buffer、Agent 重启对账、SQLite 心跳、MQTT 初连恢复等问题会直接阻断任务完成或使状态永久悬挂。
5. **真实机具控制尚未形成闭环。** 当前 `tillage_cmd` 是逻辑命令，缺少真实驱动与反馈；这属于已知能力边界，不应被描述为物理旋耕已完成。
6. **本轮不把公网安全列为主问题。** 农场/仓库专用 LAN、低速车辆和有人监管是当前明确边界；认证、TLS、证书轮换可继续后置，但掉线、重启、状态不同步仍属于局域网内的现实可靠性问题。

因此，当前版本可定义为：**有人监管下的工程联调基线，不是 L2 闭环验收版本，也不是解除真实执行器安全门禁后的生产版本。**

## 1. 场景边界与定级方法

### 1.1 已确认的现实场景

- 实车为低速履带底盘，定位使用 UM982，电机驱动支持 PWM/485。
- 边侧硬件文档后期记录为 Orange Pi 5 Pro；现场测试计划早期仍写 Orange Pi 5 Ultra，板型需要在实施前统一。
- 操作员可在约 200 米内切断驱动器主电源，边侧计算机独立供电。
- L0 为 RTK/PWM/遥控验证，L1 为单机自主，二者均不依赖云端；L2 才包含 MQTT/HTTP 云边联动。
- 现场计划要求物理急停、软件急停、0.5 秒命令超时、首次 dry-run、分阶段提速、最少一名操作员和一名安全员。
- 云端被定义为农场局域网私有云，不是公网 SaaS；用户本轮补充仓库网络同样属于受控局域网。

证据：

- [L0/L1/L2 分层](FIELD_TEST_PLAN.md#L9-L18)
- [三层急停与分阶段提速](FIELD_TEST_PLAN.md#L221-L249)
- [最少两人现场要求](FIELD_TEST_PLAN.md#L521-L529)

### 1.2 本报告的阶段化定级

| 定级 | 含义 | 当前动作 |
|---|---|---|
| **实车门禁** | 解除 `dry_run_mode` 前必须关闭，或由独立硬件保护给出可验证保证 | 不允许仅凭软件单测放行真实 PWM |
| **L2 门禁** | 不影响不启用云端的 L0/L1，但启用自动任务下发前必须关闭 | L2 不得标记为闭环可用 |
| **机具门禁** | 当前尚未接物理驱动；接入 PTO/悬挂前必须关闭 | 保持逻辑输出或人工机具操作 |
| **部署门禁** | 新目标机、systemd 或离线任务模式启用前必须关闭 | 已有人工启动环境可暂时绕开 |
| **治理项** | 不直接阻断当前有人监管试验，但会降低测试与文档可信度 | 随对应工作包收口，不扩大为架构重写 |

这种定级有意避免脱离使用阶段的笼统 P0/P1：例如云端心跳问题是 L2 门禁，但不是当前纯边侧 L0 的实车门禁；机具输入老化在尚无真实驱动时是条件问题，接入物理 PTO 后才升级为实车门禁。

### 1.3 明确不作为本轮主线的问题

- 公网零信任、TLS、复杂账户权限和证书轮换；
- 多租户、高并发、大规模车队调度；
- Kubernetes、服务网格、跨地域高可用；
- 在没有传感器的前提下实现闭环耕深控制；
- 无人值守或超出物理急停覆盖范围的自动恢复。

这些事项不是永远不做，而是在使用边界改变时重新立项，不应挤占当前停车、航向、路径与任务恢复问题的优先级。

## 3. 实车门禁问题

### SAFE-01：runtime 停止或进程崩溃时，软件不保证 PWM 回中或禁用

**定级：实车门禁。**

Runtime 停止节点时，对进程组发送 `SIGTERM`，超时后发送 `SIGKILL`：

- [进程终止策略](../edge/runtime/orchestrator/node_launcher.py#L321-L381)

PWM 节点只有在主循环正常离开并进入 Python `finally` 时才调用 `_stop_motors()` 和 `cleanup()`：

- [PWM 主循环退出与清理](../edge/nodes/io/pwm_driver/run.py#L370-L385)
- [PWM 初始化后保持 enable=1](../edge/nodes/io/pwm_driver/run.py#L155-L168)

节点没有安装自己的 `SIGTERM` handler，也没有把 PWM 安全清理注册为可在硬退出前执行的回调。隔离子进程验证结果为 `returncode=-15`，`try/finally` 内的观察输出未发生，说明默认 `SIGTERM` 不会走该清理路径；`SIGKILL`、解释器崩溃、CPU 死机或整机掉电更不可能依靠 Python 清理。

现实后果取决于目标内核 PWM 和电机控制器：如果它们在进程退出后保持最后占空比，车辆可能继续输出。仓库没有定义驱动器自身的输入超时、使能脚、失联回中或断电行为，因此这些不能被当作已有保证。

现有缓解：真机图仍为 dry-run；现场有物理断电急停。它们降低当前测试风险，但不能替代解除 dry-run 前的软硬件联合验收。

### SAFE-02：单侧 PWM 写失败可留下不对称旧输出，并伪报成功

**定级：实车门禁。**

左右 PWM 依次写入；任一步发生异常后，代码只记录日志并返回，不区分哪一侧已更新，也不把错误反馈给主循环：

- [双通道顺序写入与异常吞没](../edge/nodes/io/pwm_driver/run.py#L170-L184)
- [无条件记录 Motors stopped](../edge/nodes/io/pwm_driver/run.py#L222-L226)

随后发布的 `pwm_status` 仍是期望值，而不是硬件确认值。现实故障形态包括：左侧已写入新速度、右侧仍保持旧速度，车辆产生意外转向；或者回中写失败，但日志仍显示已停止。

该问题不要求构建复杂“事务 PWM”，但要求失败可见、不得伪报安全状态，并需要明确单侧写失败后的 fail-safe 行为。

### RTK-01：双天线航向失效后，旧航向可被无限复用

**定级：实车门禁。**

`NMEAParser` 保存 `last_heading`，但没有航向来源时间或有效期：

- [GGA 携带缓存航向](../edge/nodes/sensing/rtk_driver/nmea_parser.py#L196-L209)
- [RMC 无条件优先缓存双天线航向](../edge/nodes/sensing/rtk_driver/nmea_parser.py#L260-L282)
- [THS 无效时不清空缓存](../edge/nodes/sensing/rtk_driver/nmea_parser.py#L288-L323)

RTK 驱动只检查位置质量、卫星数和坐标范围，不检查航向有效性或年龄：

- [RTK 数据质量校验](../edge/nodes/sensing/rtk_driver/run.py#L237-L276)

复现序列：

1. 输入有效 `GNTHS=90°,A`；
2. 输入无效 `GNTHS=180°,V`；
3. 输入位置仍有效、地面航迹为 `270°` 的 RMC；
4. 输出航向仍为旧值 `90°`。

低速、停车、遮挡或双天线基线短暂异常时，这种情况具有现实概率。更关键的是，位置报文会持续刷新 pose 时间，下游 freshness 保护会认为数据仍然新鲜，却无法发现航向内容已经陈旧。

### PLAN-01：覆盖规划热更新会被消费后丢失，旧路径可继续驱动下游

**定级：L1 动态更新门禁；不阻断强制停车换任务的普通 L1。**

`global_coverage` 在持续发送旧路径的内层循环中读取新任务，识别到新任务或新 revision 后只执行 `break`，没有保存刚读到的请求：

- [内层读取新任务后直接退出](../edge/nodes/planning/global_coverage/run.py#L274-L300)

`InputPort.recv_latest()` 在返回数据时已经更新 `last_sequence`：

- [序列消费语义](../edge/sdk/port.py#L382-L397)

上游 parcel planner 和坐标转换又都只在内容变化时发送一次：

- [parcel planner 单次变化发送](../edge/nodes/planning/parcel_planner/run.py#L214-L277)
- [coord transform 单次变化转发](../edge/nodes/localization/coord_transform/run.py#L138-L162)

因此外层循环无法再取得该更新。同 ID、同 revision 的地块内容变化甚至不会触发内层退出。下游会继续基于旧路径和实时位姿产生目标，普通 target freshness 保护也无法区分“持续发布的旧路径”和“新计划”。

现实触发包括：作业中切换地块、网页修改当前边界、调整幅宽/重叠率、增加 `plan_revision`。首次现场验证应限定为停车状态切换。

## 4. L2 云边闭环门禁

### L2-01：动态地块资产写入旧目录，planner 无法读取

**定级：L2 门禁。**

TaskAssetPreparer 仍写入目录重组前的 `node-hub/parcel_planner/data/parcels`：

- [Agent 写入旧路径](../edge/agent/assets.py#L172-L180)

当前 parcel planner 固定从自身包目录 `edge/nodes/planning/parcel_planner/data/parcels` 读取：

- [Planner 实际读取路径](../edge/nodes/planning/parcel_planner/run.py#L46-L67)

现有单测把旧目录当作正确预期，因此该回归在测试中被固化：

- [错误路径被测试接受](../tests/unit/test_task_assets.py#L46-L54)

结果是：部署根不可写时任务准备直接失败；可写时文件落盘成功，但 planner 找不到地块，任务不会生成路径。

### L2-02：独立 Agent 未跟随当前 run 的数据 buffer

**定级：L2 门禁。**

数据面 buffer 已按 run 隔离；没有 `NODEFLOW_BUFFERS_DIR` 或进程内 `current_run_id` 时会回落到固定根目录：

- [buffer 目录解析规则](../edge/runtime/utils/constants.py#L58-L77)

Runtime 向节点子进程注入当前 run 环境：

- [节点 run 环境注入](../edge/runtime/orchestrator/env_builder.py#L36-L43)

但 Agent 是独立进程，没有同样的解析步骤。TaskExecutor 仍按名称读取 waypoint、pose、velocity 与 tillage 数据：

- [TaskExecutor 完成条件读数](../edge/agent/executor.py#L210-L240)

临时 run 目录复现表明，runtime 写入 `<root>/runs/<run_id>/buffers` 后，TaskExecutor 返回 `None`。控制面 `runtime.control/status` 固定在根目录，所以任务仍能启动；但进度保持 0，安全完成条件永远不成立，任务停在 `RUNNING`，多步骤作业无法推进。

### L2-03：Agent 重启后不恢复或终结遗留任务

**定级：L2 门禁。**

TaskStore 会持久化并重新加载任务，但 Agent 启动时没有对账/恢复过程：

- [Agent 启动流程](../edge/agent/agent.py#L39-L54)
- [非终态任务继续占用机器](../edge/agent/store.py#L44-L50)

重启后 executor 的 `current_task_id` 为空，心跳报告 `online`；但旧 READY/RUNNING 任务仍让新任务收到 `machine_busy`：

- [重复和 machine_busy 判定](../edge/agent/agent.py#L114-L127)
- [心跳状态来源](../edge/agent/agent.py#L245-L247)

临时 store 复现得到 `online + current_task_id='' + machine_busy` 的自相矛盾状态。原 runtime 甚至可能仍在执行，但监控和完成上报已经永久丢失。

### L2-04：SQLite 心跳离线检测抛出 aware/naive datetime 异常

**定级：L2 门禁。**

HeartbeatMonitor 使用 timezone-aware UTC 当前时间，而 SQLite `DateTime` 读回的值没有 tzinfo：

- [心跳年龄计算](../cloud/server/services/heartbeat_monitor.py#L41-L53)
- [Machine.last_heartbeat 模型](../cloud/server/models/machine.py#L15-L21)

临时 SQLite 复现结果为：读回 `tzinfo=None`，`now - last_heartbeat` 抛出 `TypeError`。循环只记录异常后继续，因此机器不会变为 offline，任务也不会进入 `communication_lost`。

### L2-05：Cloud 首次连接 MQTT 失败后不会自行恢复

**定级：L2 门禁。**

Cloud 启动时吞掉 `mqtt.connect()` 异常并继续提供 HTTP：

- [Cloud lifespan 吞掉初连异常](../cloud/server/app.py#L27-L32)

MQTT 网络循环只有在同步 `connect()` 成功后才启动：

- [MQTT connect 与 loop_start](../cloud/server/services/mqtt_client.py#L35-L38)

所以 Cloud Box/API 先启动、broker 稍后启动时，HTTP 服务可用但 MQTT 永久不可用，直到人工重启 Cloud。成功初连后的短暂断线可由 paho 自动重连缓解，本问题专指首次连接失败路径。

### L2-06：取消与离线状态不能稳定收敛

**定级：L2 门禁，低于 L2-01～L2-05。**

取消重试达到上限后只写错误信息，任务仍保持 `cancel_requested`：

- [取消超时不进入终态](../cloud/server/services/dispatch_reconciler.py#L56-L68)

Agent 收到未知任务的 cancel 时直接忽略，不回送可用于云端收敛的状态：

- [未知 cancel 被忽略](../edge/agent/agent.py#L220-L231)

这在车辆进程重启、任务 store 丢失或长时间离线后会形成永久悬挂。由于实际执行状态未知，不能简单伪装为 `cancelled`；需要评审一个明确的 `cancel_unconfirmed/communication_lost` 语义和人工处置边界。

此外，即使修复 L2-04 的 datetime 异常，HeartbeatMonitor 当前也只把 `running` 和 `cancel_requested` 转为 `communication_lost`，不会处理已经绑定机器的 `downloading/ready`；dispatch reconciler 又只重试 `pending`：

- [离线转换只覆盖两个状态](../cloud/server/services/heartbeat_monitor.py#L59-L66)
- [dispatch 重试只覆盖 pending](../cloud/server/services/dispatch_reconciler.py#L41-L54)

所以“修复时区异常”本身还不足以让所有离线任务收敛，状态转换表必须一并评审。

### L2-07：任务资产下载同步阻塞 MQTT 回调线程

**定级：L2 可靠性项；正常局域网下低于前六项。**

MQTT `_on_message()` 收到 dispatch 后同步完成任务持久化、资产下载和准备：

- [MQTT 回调直接处理 dispatch](../edge/agent/agent.py#L82-L95)
- [dispatch 内同步准备资产](../edge/agent/agent.py#L157-L180)

资产请求允许较长超时和多次重试：

- [资产下载超时与重试参数](../edge/agent/assets.py#L59-L65)
- [同步下载循环](../edge/agent/assets.py#L110-L125)

正常专用 LAN 中下载通常很快，因此它不是当前最高优先级；但 Cloud Box 不可达、HTTP 半连接或大文件传输时，会同时阻塞取消消息处理和 MQTT keepalive。该问题应在 L2 工作包中用有限后台 worker 解决，不需要引入通用任务队列平台。

### L2-08：任务完成条件硬编码为一组耕作节点

**定级：L2 契约门禁；仅影响不具备这组节点的 preset。**

TaskExecutor 要求 waypoint、pose、velocity、tillage 四类 buffer 同时存在，才可能判定完成：

- [硬编码安全完成条件](../edge/agent/executor.py#L220-L240)

当前两套耕作 preset 恰好符合该结构，但云端任务允许指定其他 `preset_yaml`。缺少 `tillage_controller`、`waypoint_selector` 或其他任一节点的合法图会永久保持 RUNNING。修复方向不应继续追加节点名，而应给任务/preset 定义明确的完成契约，或者在未声明完成契约时只提供人工终结。

## 5. 条件问题与已知能力边界

### IMPL-01：旋耕控制器不老化输入；接入真实 PTO 后可能持续输出旧工作意图

**定级：当前为机具门禁，尚非现有实车底盘门禁。**

Tillage Controller 永久缓存 pose、next point、task 和 progress，并持续用缓存计算命令：

- [输入缓存与持续输出](../edge/nodes/implement/tillage_controller/run.py#L126-L170)
- [manifest 未配置输入 watchdog](../edge/nodes/implement/tillage_controller/node.yaml#L16-L36)

底盘控制器可能已经因 pose/target 陈旧而停车，但 tillage controller 仍可保持 PTO ON/悬挂工作意图。当前真机图没有把该逻辑命令连接到真实 implement driver，所以尚未直接驱动物理 PTO；一旦接入驱动，该问题升级为实车门禁。

### IMPL-02：当前缺少真实机具驱动与反馈，逻辑状态不能证明物理完成

架构文档明确记录：`tillage_cmd` 尚未映射到真实 PWM、继电器、CAN 或 ISOBUS，且暂无限深传感器：

- [机具驱动层缺口](HEADLAND_AND_IMPLEMENT_CONTROL_ARCHITECTURE_20260529.md#L97-L103)
- [建议的驱动与反馈层](HEADLAND_AND_IMPLEMENT_CONTROL_ARCHITECTURE_20260529.md#L443-L450)

因此，现阶段不得用逻辑 `tillage_status` 推断旋耕机或悬挂已经完成物理动作，也不应宣称具备闭环耕深控制。

### PLAN-02：tillage_operation 为单输入端口配置两个来源，地块边界被静默忽略

配置同时把 `trajectory_loader.task_enu` 和 `parcel_planner.task_enu` 连接到 `coord_transform.task_enu`：

- [重复输入边](../configs/graphs/tillage_operation.yaml#L191-L204)

环境构建器只取第一条匹配边：

- [单输入只选择首个来源](../edge/runtime/orchestrator/env_builder.py#L57-L68)

结果是 parcel planner 提供的真实边界不会进入该端口，配置注释与实际行为不一致。路径段语义完整时可能被掩盖，语义缺失时 tillage controller 更容易回落到默认 work 判断。

## 6. 部署与工具链问题

### DEPLOY-01：systemd 安装脚本仍启动已移除模块

脚本生成的 service 使用：

- `python -m runtime.main`
- `python -m runtime.task.agent_main`

当前模块实际为 `edge.runtime.main` 和 `edge.agent.agent_main`：

- [错误的 systemd ExecStart](../scripts/install_edge_service.sh#L141-L175)

按仓库脚本在新目标机部署时，两项服务都会启动失败。

### DEPLOY-02：节点依赖安装器仍扫描不存在的 node-hub

安装器默认把节点根目录解析为 `<project>/node-hub`：

- [旧节点目录解析](../tools/install_node_deps.py#L139-L156)

`setup_python_env.sh` 又直接调用该脚本并报告安装完成。当前 planning 节点自己的 requirements 包含 Shapely、NumPy、pyclothoids、Flask 等根 requirements 未覆盖的依赖；干净目标机可能在安装“成功”后仍无法启动节点。

### DEPLOY-03：现场收车/回退命令仍匹配旧模块路径

**定级：现场操作门禁。**

现场测试计划的收车流程仍执行 `pkill -f runtime.task.agent_main` 和 `pkill -f runtime.main`：

- [过期的停止与确认命令](FIELD_TEST_PLAN.md#L258-L280)

当前进程模块已经是 `edge.agent.agent_main` 和 `edge.runtime.main`。旧命令可能匹配不到真实进程，使操作员误以为已经完成收车。该项应与 DEPLOY-01 同包修复，并要求停止命令之后用 NodeFlow CLI/PID/进程检查确认，而不是只依赖 `pkill` 返回值。

### CLI-01：离线 task run 的监控线程随 CLI 进程退出

`nodeflow task run` 创建局部 TaskExecutor，dispatch 后立即返回：

- [离线任务命令](../tools/cli/commands/task_cmd.py#L80-L124)

TaskExecutor 的 monitor 是 daemon thread：

- [daemon monitor](../edge/agent/executor.py#L127-L134)

CLI 随后 `sys.exit()`，监控线程终止，tasks.json 中的任务永久停在 `RUNNING`。该模式当前只能视为“向 control buffer 写入一次启动命令”，不能视为完整离线生命周期管理。

Preflight 实际启动 simulator/runtime，检查必要 buffers 和车辆移动，最后成功关闭；复核后 runtime 为 `not_running`、buffers 为空、5555/8080 无残留监听。测试和 preflight 未修改代码或配置；除本轮新增的审计/方案文档外无其他工作树变更。

### 7.2 TEST-01：为什么“全绿”没有覆盖上述问题

1. CI 只执行 quick，即 unit + cloud，未执行 integration、edge nodes 和 preflight：
   - [测试分层脚本](../tools/run_tests.sh#L1-L26)
   - [CI 测试入口](../.github/workflows/test.yml#L35-L45)
2. `pytest.ini` 排除了 MCP、simulation、legacy 等目录；其中部分旧测试已出现失效导入：
   - [pytest 收集范围](../pytest.ini#L1-L15)
3. 有测试捕获导入异常后返回 `False`，但没有断言，pytest 仍会报告通过：
   - [假绿示例](../tests/test_global_coverage_standalone.py#L65-L80)
4. 本轮关键问题恰好属于常规测试未覆盖的跨进程/跨模块行为：
   - SIGTERM/SIGKILL 是否执行硬件安全清理；
   - 双通道 sysfs 部分写失败；
   - 航向来源的有效期；
   - latest-value 请求在内外循环间的所有权；
   - Agent 与 runtime 分进程后的 run 目录解析；
   - SQLite 实际读回 datetime 的 tzinfo；
   - Agent 在不同持久任务状态下重启。
5. 本机测试环境为 Python 3.14.2，而仓库 `.python-version` 和 CI 目标是 Python 3.12；本轮不能替代目标 Linux/Orange Pi 验收。

### 7.3 测试结论的正确解释

测试结果证明当前主干不存在普遍性单元/集成回归，preflight 也证明默认仿真闭环可以工作；它们不证明真实 PWM 退出安全、L2 任务恢复或目标硬件部署已经通过。

## 8. 已确认存在的保护与已关闭旧问题

为避免重复修复或误判，本轮同时确认以下保护真实存在：

- Track Controller 使用本地单调接收时间检查 pose/target freshness，并有原地转向超时：
  - [ControlSafetyGuard](../edge/nodes/control/track_controller/atom.py#L60-L84)
  - [控制循环应用 guard](../edge/nodes/control/track_controller/run.py#L138-L209)
- PWM 进程仍存活时，上游断流由 SDK input watchdog 和节点自身 0.5 秒 command timeout 回中：
  - [PWM command timeout](../edge/nodes/io/pwm_driver/run.py#L355-L365)
- 终点到达时控制器输出精确零速度，PWM 零速度映射到中位；
- RTK 位置侧会拒绝低于配置质量、卫星不足和越界坐标；
- Runtime 使用进程组终止，SDK 有父进程死亡监控，基本孤儿进程问题已有保护；
- InputPort 自愈、run/incarnation、死亡记录、readiness、输入 watchdog、设备时间透传等 W1～W3 改造已落入当前代码；
- ENU 坐标、经纬度次序、地理航向到数学航向的主链未发现新的符号级冲突。

这些保护解释了为何 L0/L1 仿真与普通断流测试可以通过，也说明本轮无需推倒 runtime 或重写整个控制架构。当前缺口主要位于保护边界之间：进程已经死亡、内容仍更新但语义已陈旧、以及独立服务之间没有共享同一运行身份。

## 9. 实施前必须由外部信息确认的事项

以下事实无法仅靠仓库代码确定，必须由硬件、现场或产品负责人补充：

| 决策项 | 为什么必须确认 |
|---|---|
| 实际板型是 Orange Pi 5 Pro 还是 Ultra | 文档冲突，PWM chip/sysfs 映射可能不同 |
| 左右履带对应的 pwmchip/channel | 错配会直接改变转向与停车行为 |
| 电机控制器的信号丢失行为 | 决定 `SIGKILL`、CPU 死机时是否保持最后输出 |
| 是否存在使能脚、硬件 watchdog 或独立安全继电器 | 软件无法覆盖掉电和不可调度故障 |
| PWM 中值、正反向范围、死区和变化率 | 现有值仍需在目标控制器上标定 |
| UM982 THS/RMC 实际频率、状态语义和低速误差 | 决定航向超时与是否允许 ground-track fallback |
| L2 中断后的产品语义 | 决定是失败、人工确认重试还是自动重试 |
| 无物理反馈时“机具完成”的含义 | 不能把 command_sent 等同 physical_completed |
