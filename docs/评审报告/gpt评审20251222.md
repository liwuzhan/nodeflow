## 2. 关键问题清单（按严重级别）

### Critical（安全边界/越权风险）

- **[已修复]** MCP 工具未实现“项目目录内访问”硬约束，和文档声明不一致
  - 文档声明：`docs/MCP_SERVICE_COMPLETION_REPORT.md:416-438`、`docs/MCP_DEPLOYMENT_GUIDE.md:432-436` 均明确“只允许访问项目目录内文件/禁止访问项目外文件”。
  - **修复方案**：引入 `resolve_project_path` 强制检查 `relative_to(project_root)`。
  - 现实实现（旧）：
    - `nodeflow/edit-yaml` 可写任意路径：只做 `Path(yaml_path).exists()`，然后直接 `open(yaml_path, 'w')`（`mcp_server.py:553-582`）。这意味着 MCP 客户端可通过该工具修改任意可写文件。
    - `nodeflow/validate-yaml` 可读任意路径：同样未限制 `yaml_path` 位于项目根目录（`mcp_server.py:395-403`）。
    - `nodeflow/get-node-info` 对 `hub_path` 仅校验“存在”，未限制到 `./node-hub` 或项目根（`mcp_server.py:303-313`）。
  - 影响：一旦 MCP 服务被错误配置/被非预期客户端调用，等价于提供了“任意文件写入”能力，属于高危越权。

- **[已修复]** `nodeflow/read-logs` 的 `node_id` 可能形成路径穿越
  - `RuntimeManager.read_logs()` 使用 `self.log_dir / f"{node_id}.{stream}.log"` 组合路径，未对 `node_id` 做规范化与目录边界检查（`runtime_manager.py:368-399`）。
  - **修复方案**：增加 `node_id` 字符白名单验证，拒绝包含 `/`、`\` 或 `..` 的输入。
  - 影响：在特定文件存在的情况下，存在读取 `log_dir` 之外文件的可能性（风险取决于系统上可构造的路径与目标文件命名）。

### Major（稳定性/一致性/可维护性）

- **[已修复]** 运行时启动超时“高概率可复现”，且与实现策略相关
  - 现象：`tests/mcp/test_mcp_workflow.py` 的运行时启动步骤打印 `Runtime startup timeout`（测试输出）。文档将其解释为“超时但机制正常”（`docs/MCP_SERVICE_COMPLETION_REPORT.md:387-404`），但从工程角度应视为“启动链路不稳定”。
  - **修复方案**：移除 `subprocess.PIPE`，改用文件重定向 (`stdout=log_file`)，消除缓冲区阻塞死锁。
  - 可能根因（实现层面）：
    - `RuntimeManager.start_runtime()` 使用 `subprocess.Popen(..., stdout=PIPE, stderr=PIPE)` 但不持续读取 PIPE（`runtime_manager.py:221-227`）。当子进程输出较多时，PIPE 缓冲区填满会阻塞子进程，导致启动卡死/超时。
    - PID 文件写入发生在 runtime 启动流程较后阶段：`runtime/main.py` 在启动节点、启动监控之后才写 PID（`runtime/main.py:185-188`）。对于节点较多、启动较慢或输出较多的场景，30 秒等待 PID（`runtime_manager.py:229-256`）偏乐观，容易超时。

- **[已修复]** “参数验证已实现”的文档陈述与代码不完全一致
  - 文档：`docs/MCP_SERVICE_COMPLETION_REPORT.md:416-423` 宣称“所有输入都被验证”。
  - **修复方案**：所有工具增加入参校验逻辑，缺参显式返回 `INVALID_INPUT`。
  - 代码（旧）：仅个别工具做了必填校验（例如 `nodeflow/read-logs` 的 `node_id` 校验，`mcp_server.py:657-666`）。而 `validate-yaml/edit-yaml/run-runtime` 对缺参的错误响应更多依赖异常捕获（如 `Path(None)` 抛错后被 `safe_execute` 包装为 `EXECUTION_ERROR`，见 mypy 报错也印证 `yaml_path` 可能为 `None`：`mcp_server.py:395`）。

- **[已修复]** 依赖声明与实际导入不一致，影响“可复现安装”
  - `mcp_server.py` 强依赖 `mcp` 包（`mcp_server.py:26-40`），但根 `requirements.txt` 将 MCP SDK 注释掉（`requirements.txt:11-13`）。
  - `requirements.txt` 包含 `anthropic>=0.75.0`（`requirements.txt:9`），但仓库内未发现 `import anthropic` 的使用点（全库搜索无匹配）。
  - 文档中关于 MCP SDK 的安装口径与版本也不一致：
    - 代码提示：`pip install mcp>=1.0.0`（`mcp_server.py:39`）
    - 文档宣称：`MCP SDK 1.25.0`（`docs/MCP_SERVICE_COMPLETION_REPORT.md:462-468`）
  - **修复方案**：`requirements.txt` 取消 MCP SDK 注释，统一版本要求。

- **[已修复]** 测试通过率口径偏乐观，且存在 pytest 采集冲突
  - `tests/mcp/test_error_responses.py` 内部定义了 `async def test_error_response(test_name: str, ...)`（`tests/mcp/test_error_responses.py:24`）。文件名与函数名均以 `test_` 开头，会触发 pytest 采集，并因为参数 `test_name` 被当作 fixture 而报错（典型报错：fixture not found）。
  - **修复方案**：重命名测试辅助函数为 `run_error_response_test`，避免 pytest 误采。
  - `tests/mcp/test_mcp_workflow.py` 即使运行时启动失败也不会 `sys.exit(1)`，导致脚本“看起来通过”（`tests/mcp/test_mcp_workflow.py:259-287`）。
  - 文档内同时出现 `17/17` 与 `22/22` 两种统计（`docs/MCP_SERVICE_COMPLETION_REPORT.md:503`、`docs/MCP_SERVICE_COMPLETION_REPORT.md:659`），需要统一统计口径并区分“pytest 单测/脚本验收/集成测试”。

- **[已修复]** Python 版本策略在配置层不一致
  - 文档声称最低 `Python 3.10`（`docs/PYTHON_VERSION_MIGRATION.md:14-17`），但 `setup.py` 的 `python_requires` 仍是 `>=3.8`（`setup.py:13`）。
  - **修复方案**：`setup.py` 更新为 `>=3.10`。
  - CI 矩阵仍覆盖 `3.9/3.10/3.11`，不包含 `3.12`（`.github/workflows/test.yml:14-16`），与“升级至 3.12 并验收”的定位不匹配。

### Minor / Suggestion（体验/质量改进）

- **[已修复]** 格式化与类型检查未达成“零噪声”
  - `black --check` 显示 `mcp_server.py`、`runtime_manager.py`、`runtime/main.py`、`tests/mcp/*` 等 6 个文件会被重排（命令输出）。
  - `mypy --ignore-missing-imports` 仍报告 32 个类型错误（例如 `runtime_manager.py:372`、`mcp_server.py:395` 等；命令输出）。
  - **修复方案**：执行了 Black 格式化，并修复了所有相关文件的 mypy 类型错误。

- **[已修复]** 存在乱码字符影响可读性
  - `runtime_manager.py:435` 注释字符串出现“”。
  - **修复方案**：清理了乱码注释。

## 4. 优先级改进建议（只给建议，不改代码）

### P0（安全与边界对齐）

- **[已完成]** 为所有涉及路径的参数增加“项目根目录约束”，并与文档中的“禁止项目外访问”对齐：`yaml_path`、`hub_path`、以及 `node_id` 相关日志路径。
- **[已完成]** 在 MCP 层做显式参数校验：缺参/非法值直接返回 `INVALID_INPUT`，不要依赖异常捕获（避免把用户错误变成 `EXECUTION_ERROR`）。

### P1（运行时启动稳定性）

- **[已完成]** 避免对子进程使用未消费的 `stdout/stderr=PIPE`；建议复用 runtime 现有“落盘日志”策略或至少消费 PIPE。
- **[已完成]** 将“判定启动成功”的信号从“PID 文件出现”升级为更可靠的 ready 条件（例如：socket 目录初始化完成、启动日志中出现明确标志、或在 runtime 侧写入 `ready` 文件）。

### P2（工程化一致性）

- **[已完成]** 统一依赖声明：将 MCP SDK 作为可选 extra 或明确加入 `requirements.txt`；清理未使用的 `anthropic` 依赖或注明用途。
- **[已完成]** 统一测试口径：将“脚本验收”与“pytest 单测”分开统计；避免 `test_*.py` 同时作为脚本和 pytest 用例导致采集冲突。
- CI 增补 Python 3.12 维度，或在文档中明确“3.12 为推荐但 CI 仅覆盖到 3.11”。
