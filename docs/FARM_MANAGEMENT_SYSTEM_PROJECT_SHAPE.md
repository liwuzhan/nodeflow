# 农场管理系统项目形态草案

> 状态: 想象基线 / 新项目种子文档
> 日期: 2026-06-29
> 目的: 从 NodeFlow 当前云边能力中抽离出一个独立“农场管理系统”项目的产品形态、系统边界和演进方向。

## 1. 一句话定义

农场管理系统不是单纯的云端控制台，也不是车辆运行时。它是一个面向农场现场的作业经营系统:

- 管地块
- 管机器
- 管作业
- 管人和班次
- 管作业结果
- 管现场设备连接
- 把“要做什么”稳定地下发给车端
- 把“做得怎么样”收回来并形成可追踪记录

NodeFlow 是车端运行和云边任务执行框架；农场管理系统是围绕农业生产组织的上层业务系统。

## 2. 项目边界

### 2.1 这个系统负责什么

- 农场基础资料: 农场、地块、作物、作业季、机具、车辆、操作员
- 地图和空间数据: 地块边界、障碍物、作业区域、地头区、禁入区
- 作业计划: 创建任务、拆分地块、分配机器、设置步骤依赖
- 作业执行: 下发任务、暂停/取消/重试、查看实时状态
- 结果回收: 轨迹、覆盖率、面积、耗时、异常、人工备注
- 现场部署: 局域网 Cloud Box、OpenWrt、边侧设备接入
- 基础运维: 设备在线状态、版本、日志摘要、备份恢复

### 2.2 这个系统暂时不负责什么

- 车端低层控制算法
- 具体传感器驱动
- 电机、液压、PTO、底盘控制细节
- NodeFlow runtime 的节点编排实现
- 完整 ERP / 财务 / 农资库存系统
- 大规模公网 SaaS 多租户计费体系

这些可以连接，但不是第一阶段核心。

## 3. 核心用户

### 3.1 农场负责人

关心:

- 今天有哪些作业
- 哪些地块完成了
- 哪台车在干什么
- 有没有异常
- 成本、效率、覆盖质量如何

需要的界面:

- 总览看板
- 作业日历
- 地块和作业结果
- 机器状态

### 3.2 现场操作员

关心:

- 当前该启动哪台车
- 车有没有连上系统
- 作业是否下发成功
- 出错后怎么恢复

需要的界面:

- 机器确认注册
- 作业下发/暂停/取消
- 异常提示
- 简单操作流程

### 3.3 调试/维护人员

关心:

- 网络是否通
- MQTT 是否通
- 车端服务是否在线
- 任务卡在哪一步
- 日志和数据 buffer 有没有变化

需要的界面:

- 设备诊断
- 服务状态
- 日志摘要
- 任务链路追踪
- 配置导出/导入

## 4. 产品形态

### 4.1 第一阶段: 农场局域网私有云

默认部署在农场本地:

```text
OpenWrt Router
  - 专用 WiFi
  - DHCP / local DNS
  - Cloud Box 静态域名
  - 出网白名单

Cloud Box
  - Farm Management API
  - Web Console
  - MQTT Broker
  - Local Database
  - File Storage

Edge Vehicles
  - NodeFlow Runtime
  - TaskAgent
  - Sensors / Drivers
```

这个阶段不追求公网 SaaS，目标是现场可靠、能交付、能调试。

### 4.2 第二阶段: 可选远程同步

农场本地仍是主系统，公网云只做:

- 远程备份
- 远程只读查看
- 软件更新
- 跨农场数据汇总
- 维护人员远程诊断入口

原则: 车端作业不依赖公网。

### 4.3 第三阶段: 多农场经营系统

当多个农场部署后，再考虑:

- 多农场账号
- 统一设备资产管理
- 作业成本和产能分析
- 农艺数据沉淀
- 服务商维护后台

## 5. 系统模块

### 5.1 地块管理

能力:

- 创建/编辑地块边界
- 导入 GeoJSON/KML/Shapefile
- 记录地块面积、作物、季节、备注
- 标注障碍物、禁入区、入口点、地头区
- 地块版本管理

关键对象:

- `Farm`
- `Field`
- `FieldBoundary`
- `Obstacle`
- `Headland`
- `FieldVersion`

### 5.2 机器管理

能力:

- 自动发现机器
- 人工确认注册
- 机器状态: 未注册、在线、忙碌、离线、维护中
- 机器能力: 作业幅宽、速度范围、机具类型、版本
- 服务状态: runtime、agent、MQTT、定位、底盘

关键对象:

- `Machine`
- `MachineCapability`
- `MachineHeartbeat`
- `MachineServiceStatus`
- `MachineVersion`

### 5.3 机具管理

能力:

- 记录旋耕机、播种机、喷洒设备等机具
- 维护作业幅宽、重叠率、作业速度、挂接方式
- 与机器绑定或临时挂接

关键对象:

- `Implement`
- `ImplementProfile`
- `MachineImplementBinding`

### 5.4 作业计划

能力:

- 创建作业
- 选择地块
- 选择作业类型
- 设置多步骤链路: 旋耕 → 播种 → 喷洒
- 地块分割
- 多机分配
- 预计面积、耗时、路径长度

关键对象:

- `Job`
- `JobStep`
- `JobAssignment`
- `FieldSplit`
- `OperationPreset`

### 5.5 作业执行

能力:

- 下发作业到边侧
- 任务 ACK
- 状态回传
- 多步骤自动推进
- 暂停、恢复、取消、重试
- 现场异常记录

关键对象:

- `Dispatch`
- `EdgeTask`
- `TaskStatusEvent`
- `TaskAck`
- `TaskError`

### 5.6 作业结果

能力:

- 记录实际轨迹
- 计算覆盖面积
- 计算重复率、漏作区域
- 统计耗时、平均速度、暂停时间
- 生成作业报告

关键对象:

- `JobResult`
- `CoverageMap`
- `TrackLog`
- `OperationMetric`
- `ExceptionRecord`

### 5.7 现场网络和部署

能力:

- 显示 Cloud Box 地址
- 显示 OpenWrt 状态
- 生成边侧安装命令
- 记录部署配置
- 备份/恢复本地数据

关键对象:

- `SiteNetwork`
- `CloudBox`
- `RouterConfig`
- `EdgeInstallProfile`
- `BackupSnapshot`

## 8. 和 NodeFlow 的关系

农场管理系统不应该直接吞掉 NodeFlow，而应该把 NodeFlow 当成边侧执行平台。

### 8.1 农场管理系统负责

- 业务对象
- 地图和地块
- 作业编排
- 多机分配
- 结果记录
- 人机界面
- 现场运维

### 8.2 NodeFlow 负责

- 车端节点图
- 数据流端口
- runtime daemon
- 任务接收
- 参数注入
- 进程管理
- buffer 和日志

### 8.3 接口边界

农场管理系统通过稳定协议控制 NodeFlow:

- MQTT task dispatch/cancel
- MQTT heartbeat/status/ack
- HTTP file download: 地块、路径、配置
- 后续可增加诊断 API: buffer 状态、节点健康、版本

## 9. MVP 范围

第一版只做“能下地干活”的最小系统。

### 9.1 必须有

- 地块 CRUD
- 地图绘制地块
- 机器自动发现和确认注册
- 作业创建
- 地块分割
- 多机分配
- 任务下发
- 状态回传
- 多步骤推进
- 作业取消/重试
- 基础作业结果记录
- LAN 部署配置说明

### 9.2 可以没有

- 多租户账号体系
- 精细权限
- 财务/库存
- 复杂报表
- 公网远程控制
- AI 决策推荐
- 完整农艺模型

### 9.3 MVP 验收

- Cloud Box 和 1 台车在局域网内完成自动发现
- 创建一个地块
- 创建一个单步骤作业
- 下发到车端
- 收到 ACK 和状态回传
- 任务完成后生成基本结果
- 再创建一个两步骤作业，第一步完成后自动推进第二步
- 2 台车时可以分割地块并分别下发

## 10. 技术形态建议

### 10.1 后端

优先简单、可部署:

- FastAPI
- SQLite 起步，后续 PostgreSQL/PostGIS
- SQLAlchemy
- MQTT client
- 本地文件存储
- 可选任务队列，先不引入复杂调度系统

### 10.2 前端

- Vue 3 + TypeScript
- 地图: Leaflet 起步
- 状态管理: Pinia
- UI: Element Plus 或更轻量的自定义组件
- 第一阶段重视操作效率，不做营销型页面

### 10.3 地图和空间能力

起步:

- GeoJSON
- Shapely
- Leaflet

后续:

- PostGIS
- 离线瓦片
- 地块版本 diff
- 覆盖率栅格/矢量混合表达

### 10.4 部署

第一阶段:

- OpenWrt 专用路由器
- Cloud Box 本地部署
- Edge systemd 服务
- 本地备份

后续:

- Docker Compose
- OTA 更新
- 远程备份
- 维护隧道

## 11. 风险和关键判断

### 11.1 最大风险不是功能，而是现场可靠性

需要优先处理:

- 网络掉线
- 机器重启
- Cloud Box 重启
- MQTT 重连
- 任务重复下发
- 状态不同步
- 操作员误操作

### 11.2 不要过早做 SaaS

农场现场首先要能在没有公网的情况下完成作业。公网能力应该是增强项，不是基础依赖。

### 11.3 不要把车端调试藏起来

系统必须能让维护人员快速看到:

- 机器是否在线
- agent 是否在线
- runtime 是否在线
- 当前任务是什么
- 最近错误是什么
- 数据是否在流动

### 11.4 不要把 ROS2 作为默认依赖

如果有必须复用的 ROS2 节点，可以通过 bridge 接入。但低速农业车当前不需要为了“标准机器人生态”引入整套 ROS2。

## 13. 项目命名候选

暂定方向:

- FarmFlow
- NodeFarm
- FieldOps
- AgroFlow
- FarmOps

命名上最好避免过度强调机器人，系统本质是农场作业管理。

## 14. 当前结论

这个系统应该独立成项目。NodeFlow 保持为车端执行和数据流框架；农场管理系统围绕农场业务对象、作业计划、现场部署、结果记录展开。

第一阶段目标不是做大而全平台，而是做一个能在专用局域网内稳定完成农场作业组织和云边下发的本地系统。
