## 2. 评审裁决

### 2.1 支持最小计划为主线的四条理由

1. **架构论证成立**：Cordis 的核心机制（进程内 Fiber、响应式 inject/provide）偿还的是"选择单进程组件模型"的代价；NodeFlow 已选择进程隔离，没有这个债。资源收口的真实缺口是 F-1/F-2 量级（几十行），不是一个 effect 栈。
2. **与项目阶段匹配**：0803 评审已定边界为"有人监管的边侧上机实测"，且当时已将 CLI 启动竞态与 InputPort 重同步定为当前 P1 / 量产前 P1。最小计划是已接受路线的收口；Cordis 报告的 M3/M6/M7 对应的需求（第二定位源在线切换、作业中改图、同机双 runtime）今天不存在。
3. **死亡记录是最高价值交付物且只有一方看到**：农机每日断电 + 日志在 /tmp（F-7）+ 崩溃只留一行日志，三者叠加意味着现场故障永远查不了第二次。Cordis 报告通篇未覆盖"断电后证据归零"。
4. **工程诚实度**：最小计划行号级可复核，且修正了讨论中的口头错误结论（其 §2.2 时间戳逐跳漂移，经核实属实：`rtk_filter/atom.py:59` 以本地墙钟覆盖设备时间）。

1. **§10 风险表**（心跳抖动震荡、provider 双活、reconcile 重入）——当最小计划 §4 的触发条件命中、真的要做响应式机制时，作为设计评审 checklist；

3. **§12 验收指标的可测量表述**（"拒绝旧世代比例 100%""资源回到基线"）——合并进最小计划 §5。

## 3. 补强设计 D1：框架/节点责任边界（三问测试）

### 3.1 判定标准

任何职责按顺序问三个问题，答案直接决定归属：

1. **幸存者测试**：对应故障发生时，谁还活着？
2. **信息位置测试**：该事实是否需要节点配合才能获得？
3. **重复实现测试**：若每个节点各写一遍，是否逐字相同？

### 3.2 归属清单

**框架（runtime）必须负责——幸存者测试失败，别人办不了：**

| 职责 | 理由 |
|---|---|
| 死亡记录与现场快照 | 节点被回收后无法处理自己的遗留物 |
| 复活与重试预算 | 同上；F-1/F-2 证明这是当前最脆弱一环 |
| run_id / incarnation 分配 | **框架是唯一知道"这是第几次拉起"的实体**；重启回调走 `launcher.launch`（`main.py:402-417`），每次重建 env（`env_builder.py`），注入 `NODEFLOW_INCARNATION` 是一行的事 |
| 启动排序、回滚、readiness 门控 | 先存性：框架先于节点存在 |
| 跨节点聚合视图（status） | 没有任何单个节点看得见全图 |
| 清场与保留策略 | 跨 run 管辖权 |

**SDK 必须负责——重复实现测试逐字相同的部分：**

已收编：心跳发射（`:215-217`）、父进程看门狗（`:34-93`）、结构化清理（`shutdown`/`__exit__`，`:443-476`）、参数解析、schema 校验开关。最小计划将收编：write_ts 盖戳、InputPort 重连状态机、输入看门狗**机制**。**本报告新增**：

- **`sdk.die(reason, code=1)`**——P2"病了就大声死"的 SDK 落点。现状：清理侧不缺——SDK 已有结构化清理（`shutdown()`，`nodeflow_sdk.py:443`；`__enter__/__exit__`，`:472-476`），25/26 个节点经 `with NodeFlowSDK(...)` 使用；`nodeflow_sdk.py:105-108` 是父进程看门狗检测到父死后的退出路径（手动 `atexit._run_exitfuncs()` + `os._exit(1)`）。**缺的是"大声"**：节点致命退出只能各自在最外层 `except` 手写 `traceback + sys.exit(1)`（全仓 8 处，如 `pwm_controller/run.py:162`、`global_coverage/run.py:338`），遗言格式不一；且 `sys.exit` 在非主线程调用仅终止调用线程、不终止进程——心跳线程继续报活，形成假存活。`sdk.die` 统一为：结构化 stderr 遗言（含 node_id、原因、关键端口年龄）→ flush → `os._exit(code)`（任意线程可调用）。心跳随进程冻结即为死亡信号，死亡记录的 `stderr_tail` 自动获得高质量遗言。规模 ~15 行。

**节点必须自己负责——信息位置测试，框架拿不到业务语义：**

| 职责 | 为什么框架替代不了 |
|---|---|
| "我病了"的判定 | RTK 失锁、串口僵死、相机无帧——只有节点认识自己的设备 |
| 安全态的**内容** | pwm=0 还是保持姿态是业务知识；框架可强制"超时必须做点什么"（W3-3 机制），不能决定"做什么"（pwm_driver `command_timeout=0.5s` 为现有原型，`run.py:54,344-350`） |
| 业务 readiness 声明 | first_output 是否代表就绪只有节点知道 |
| 设备时间透传纪律 | payload 时间戳语义是业务约定（W3-1 修 `rtk_filter` 属此类） |

**一句话边界：框架负责"事实与后事"，节点负责"病情与遗言"。** 框架永不解释 payload 的业务含义；节点永不复活自己、永不动全局状态。

## 4. 补强设计 D2：重启后的内存池策略

### 4.1 前提：单写者 = 结构性失败隔离

每个 buffer 的唯一写者是其生产节点。节点 X 重启，受影响的**只有 X 自己的输出池**；下游的输入端只是别人文件的 mmap 映射，无池可分配；上游完全无关。因此"对上下游做一样的操作"这个选项**不存在**——若强行级联重建，等于把单点故障放大成全图重连风暴（Cordis 报告 §10 警告的震荡）。池的所有权归写者，问题只剩"被拉起节点自己的输出池怎么办"。

### 4.2 三条路线对比

| 路线 | 机制 | 后果 |
|---|---|---|
| A. 复用（现状） | `create = not exists`，seq 续写（N-1） | 零成本；世代不可见，陈旧与新鲜数据在 seq 上无缝拼接 |
| B. 每次重拉建新文件 | unlink + 新建，新 inode | 下游旧 mmap 指向已 unlink 的 inode，看到**永久冻结的 seq**——不主动重映射即永久静默断流。W2-3 的 inode 检测从安全网变成关键路径，每次重启都赌所有下游及时察觉 |
| C. 复用 + incarnation | 框架发放世代号，走控制面 | 数据面零改动；归因完整 |

### 4.3 决策：默认 C；仅两个例外走"改名留证重建"

**默认复用**。latest-value 语义下每条 payload 是全量快照，崩溃前后数据"拼接"语义无害；真正需要世代的是**归因**（这份数据是哪个生产者世代写的），而归因不需要重建内存池——框架本来就知道世代（重启是它发的），health 通道本来就在周期广播。

**incarnation 机制**：

- runtime 侧：NodeMonitor/launcher 维护每节点 `incarnation` 计数（初值 1，每次重拉 +1），经 env `NODEFLOW_INCARNATION` 注入；与 RetryTracker 的崩溃计数同生命周期，新 run 随 run_id 重置；
- SDK 侧：`report_health` 增加 `incarnation` 字段（节点零改动）；
- 消费侧：CLI status、死亡记录、W2-3 的端口摘要引用 health 中的 incarnation 做归因，**不进数据面 header**（W2-1 维持 16 字节不变）。

**例外：改名留证重建**——仅当 SDK 打开旧 buffer 时发现以下任一情况：

1. 打开/mmap 失败（文件损坏）；
2. header 内容非法（length 越界等撕裂痕迹）；
3. **文件尺寸与配置不符**（顺手修复 N-2：尺寸变更在单节点重启时静默不生效）。

处置：旧文件改名为 `<name>.dead.<incarnation>.buf` 留证（不删除），新建同名池。下游经 W2-3 的 inode 检测重映射恢复——此路径罕见，inode 触发器降级为安全网恰如其分。死亡记录应引用被隔离的文件名。

### 4.4 与既有工作项的关系

- **W2-2 的 run 作用域路径（`/tmp/nodeflow/<run_id>/buffers`）落地后，跨 run 污染结构性消失**，F-8 的清场毁现场问题大部分消解：旧 run 目录整体保留即为现场，W3-2 退化为"保留最近 5 个 run 目录 + 超限时先快照死亡 run 再剪除"。Q5 的清场默认值之争随之简化：**run 内不清理任何 buffer（单写者独占），跨 run 靠目录隔离**。
- 复用策略与 W3-2 不冲突：复用是 run 内单节点重启语义；快照是跨 run 证据保留。

## 5. 补强设计 D3：生前遗嘱与死亡记录语义修正

### 5.1 死后证据的可信度分级（定量依据 N-4）

| 证据 | 死后状态 | 可信度 |
|---|---|---|
| 死节点**自己的输出 buffer** | 写者已死，无人覆写，冻结于最后写入 | **完全可信**；`output_ages_ms` 可靠 |
| 死节点的 **health buffer** | 同上冻结；最后心跳时间戳给出精确死亡时刻（误差 ≤2s） | **完全可信** |
| 死节点的**输入 buffer**（上游所写） | 上游仍活着，检测延迟 ~1.1s 内已被覆写约 20 代（20 Hz） | **"节点死前读到的那条输入"在 latest-value 语义下设计上不可恢复**；只有"检测时刻上游活性"有意义 |

结论：`input_ages_ms` 的语义必须**如实标注**为"检测时刻的上游活性"——年龄 ≈0 说明"非饿死，是自己卡死"；年龄巨大说明"饿死嫌疑"。想恢复 payload 级输入现场只能加日志环，那是否定 latest-value 传输语义本身，不做（§8 登记）。

### 5.2 但"饿死还是卡死"不能只剩推断：生前遗嘱

现有方案的诚实性漏洞：框架在检测时刻读到"上游陈旧 41s"，只能**推断**节点死前被饿死——无法排除上游是在这 1.1s 窗口内刚卡住。堵法不是抢已被覆写的现场，而是**让节点活着时自己记录消费位置**：

**health payload 增强**（`report_health`，`nodeflow_sdk.py:311-335`）：

```json
{
  "status": "ok", "node_id": "...", "timestamp": ..., "heartbeat_interval": 2.0,
  "incarnation": 3,
  "inputs": {
    "rtk_fix": {"connected": true, "last_seq_seen": 88231, "source_write_age_ms": 45},
    "serial_raw": {"connected": true, "last_seq_seen": 1204, "source_write_age_ms": 41000}
  },
  "outputs": { "...": true }
}
```

- `inputs` 由布尔升级为结构体（health payload schema v2，CLI `health_cmd` 同步适配；64KB health buffer 容量无虞）；
- `last_seq_seen`：InputPort 现成字段（`port.py:159`）；
- `source_write_age_ms`：依赖 W2-1 的 `last_write_age_ms()`，为零成本读取；
- 节点死亡瞬间 health 冻结，这份"截至死前 ≤2s，我的输入 serial_raw 已陈旧 41s"的**生前证词**随遗言留下。

### 5.3 死亡记录 schema 修订（W2-4）

```json
{
  "ts_wall": "...", "run_id": "...", "node_id": "rtk_sensor",
  "package": "sensing/rtk_driver", "incarnation": 3, "retry_count": 2,
  "exit_code": 1, "signal": null,
  "stderr_tail": "…≤500 字…",

  "will": {
    "health_age_ms_at_crash_detect": 1200,
    "inputs": { "serial_raw": {"last_seq_seen": 1204, "source_write_age_ms": 41000} }
  },
  "witness": {
    "output_ages_ms": {"rtk_fix": 41200},
    "input_ages_ms_note": "检测时刻上游活性，非节点死前所见",
    "input_ages_ms": {"serial_raw": 42000}
  },
  "quarantined_buffers": []
}
```

- `will` = 节点生前证词（冻结 health 的摘录）——"饿死还是卡死"的**主证据**；
- `witness` = 框架目击者账户（退出码、stderr、检测时刻年龄）——**旁证**；
- 两者互相印证：遗嘱说输入已陈旧 41s、检测时仍陈旧 → 饿死成立；遗嘱说输入新鲜、检测时也新鲜 → 自己卡死成立。推断升级为证词。

## 7. 验收标准增补（接最小计划 §5）

11. 重启任一节点 → 其 health `incarnation` 递增，status 输出与当次死亡记录引用一致；
12. 构造损坏 buffer（垃圾 header / 尺寸不符）→ 节点启动时旧文件改名留证、新池建立、下游 ≤2 个轮询周期恢复，死亡记录引用被隔离文件名；
13. 强杀上游节点 → 死亡记录 `will.inputs` 含 `last_seq_seen` 与 `source_write_age_ms`，且与 `witness.input_ages_ms` 互相印证；
14. 强杀任一节点 → 其冻结 health 的时间戳距框架检测时刻 ≤ 心跳间隔 + 检测周期（≤3s），死亡时刻可定位；
15. health payload v2 下旧版 CLI 不崩溃（缺字段降级显示）。

## 8. 明确不做（追加登记）

| 机制 | 理由 | 触发条件 |
|---|---|---|
| 输入 payload 级取证（journaling ring） | 否定 latest-value 语义本身，成本高 | 出现必须复盘"节点死前读到的那一条"内容的事故 |
| 每次重启强制建新池（路线 B） | 下游重映射变关键路径，代价大于收益（§4.2） | 复用路径被证明产生实际世代混淆事故 |
| 级联重建上下游池 | 单写者模型下结构性不需要（§4.1） | 永不；若出现此需求说明单写者假设已被破坏 |
| payload 业务时间戳的全仓治理 | W3-1 已覆盖主链漂移点；其余逐节点约定 | 出现依赖 payload 时间戳做跨节点时序分析的需求 |
