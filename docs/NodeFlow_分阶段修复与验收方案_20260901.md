# NodeFlow 分阶段修复与验收方案：实车安全与云边闭环

> 方案日期：2026-09-01  
> 方案基线：`master` @ `9108b81`  
> 文档状态：**DRAFT / FOR REVIEW；待多方评审，未批准实施**  
> 问题依据：[NodeFlow 全仓审计报告：实用边界与风险复核](NodeFlow_全仓实用边界审计报告_20260901.md)  
> 适用边界：低速履带式农用车辆、有人现场监管、物理急停、农场/仓库专用局域网  
> 约束：本方案不授权代码、配置或硬件改动；每个工作包必须独立评审并达到 Go 条件后才可实施

---

## 0. 本方案的定位

本方案把审计中已确认的问题转化为**候选工作包、评审问题和验收门槛**。它不是一份要求立即执行的任务清单，也不代表所有候选设计已经定案。

总体顺序：

1. 先确认硬件事实和故障语义；
2. 再关闭真实执行器、航向和路径更新门禁；
3. 然后恢复 L2 云边任务闭环；
4. 最后收口部署、CLI 和测试可信度；
5. 真实 PTO/悬挂驱动单独立项，不混入底盘整改。

在阶段门槛通过之前：

- `planning_with_real_rtk.yaml` 保持 `dry_run_mode: true`；
- 首次真实输出只允许在电机离地/台架状态进行；
- 不宣称 L2 自动任务闭环可用；
- 不宣称逻辑 `tillage_status` 等于机具物理完成；
- 不把物理急停当成软件问题可以不修的理由，也不把软件清理当成硬件失效保护的替代品。

## 1. 目标、原则与非目标

### 1.1 目标

- 让 runtime 正常停止、节点退出和单通道 I/O 故障具有明确的执行器安全结果；
- 让 RTK 航向的来源、有效性和年龄可被控制链识别；
- 让路径更新遵守 latest-value 语义而不丢请求、不继续静默使用旧计划；
- 让 L2 动态资产、run buffer、重启、掉线、取消和 MQTT 启动顺序可以收敛；
- 让干净目标机按仓库脚本可部署，让公开 CLI 行为与文档一致；
- 让每项改动都有自动测试、故障注入、目标机或现场验收和回滚条件。

### 1.2 裁决原则

| 原则 | 具体含义 |
|---|---|
| **现实风险优先** | 优先处理低速农机实际会遇到的停止、遮挡、掉线、重启和操作切换，不用理论攻击面挤占资源 |
| **阶段绑定** | L0/L1、L2、真实机具分别设置门禁，不要求未启用模块阻塞全部测试 |
| **最小可验证改动** | 复用现有 watchdog、run_id、TaskStore、MQTT 客户端和状态机，不引入新平台 |
| **失败显式** | 无法确认安全或完成时进入明确的 failed/interrupted/communication_lost，不伪报成功 |
| **默认不自动续跑** | 车辆相关进程重启后，除非未来另行批准，不自动恢复可能产生运动的任务 |
| **软硬件分层** | `SIGTERM` 等可调度路径由软件负责；`SIGKILL`、CPU 死机、掉电和信号线故障必须由独立硬件保护覆盖 |
| **证据先于放行** | 单测通过只能进入下一验证层，不能直接解除 dry-run |
| **一包一责** | 每个工作包独立提交、测试和回滚，不混入目录美化或大范围重构 |

### 1.3 明确非目标

- 公网级认证、TLS、证书轮换和零信任；
- 多 Cloud Box 高可用、跨地域部署和大规模车队调度；
- Kubernetes、服务网格、通用工作流引擎；
- EKF/IMU 全量融合或定位框架重写；
- 在没有反馈传感器时实现闭环耕深；
- 无人值守和远程自动恢复；
- 一次性修复全部历史 MCP、旧 simulation 和 legacy 测试；
- 与本轮问题无直接关系的全仓目录或抽象层重构。

## 3. 多方评审与实施流程

### 3.1 评审角色

| 角色 | 主要责任 |
|---|---|
| Runtime/SDK 维护者 | 进程退出、run/buffer、端口与 CLI 契约 |
| 控制与规划负责人 | 停车、旧路径、规划切换、控制器安全状态 |
| RTK/定位负责人 | UM982 报文语义、航向有效期和 fallback 条件 |
| Cloud/Edge Agent 负责人 | 任务状态机、重启对账、MQTT 与资产生命周期 |
| 硬件/电气负责人 | 板型、PWM 映射、驱动器失联行为、硬件 watchdog/使能回路 |
| 测试负责人 | 故障注入、收集范围、目标 Python/Linux 与证据归档 |
| 现场操作员 | 操作流程是否可执行、异常是否可识别 |
| 现场安全负责人 | 急停、人员站位、速度和最终 Go/No-Go |

同一人可以承担多个角色，但 WP-A1 的 Go 不能只有软件开发者签字，必须包含硬件/电气和现场安全意见。

### 3.2 四轮评审

1. **事实评审**：确认审计证据、适用阶段、是否存在未记录的硬件保护；不讨论大改造。
2. **方案评审**：在每个工作包的候选方案中作出选择，补齐参数和状态语义。
3. **实现与测试评审**：按独立提交审查代码、测试、失败注入和回滚方式。
4. **现场放行评审**：自动化和台架通过后，由操作员、安全负责人和对应技术负责人决定 Go/No-Go。

### 3.3 验证层级

任何涉及运动或机具的工作包依次通过：

```
单元/集成测试
    → 进程与 I/O 故障注入
        → 目标板 dry-run
            → 电机离地/执行器离机台架
                → 空旷区域最低速度
                    → 受控观察期
```

任何一级出现残留输出、旧航向、旧路径、状态悬挂或无法解释的自动续跑，立即回到 No-Go。

## 4. 阶段 A：真实车辆安全与核心控制

### WP-A1：执行器安全退出与 PWM 错误透明化

**目标**

- Runtime 正常 stop、stop-dataflow、节点收到 `SIGTERM`、节点主循环异常时，两路 PWM 在约定时间内进入已验证的安全状态；
- 左/右任一通道写失败时不得继续伪报正常，也不得无条件记录“Motors stopped”；
- 明确软件可保证的故障集合，以及必须由硬件保证的集合。

**非目标、依赖与评审**

- 非目标：用 Python 承诺 `SIGKILL`、CPU 死机或掉电安全，或重写整个 launcher；
- 依赖：真实板型、PWM 映射、中值和电机控制器失联行为；
- 必须评审：Runtime/SDK、控制、硬件/电气、测试、现场安全。

**候选方案**

1. 在 PWM 节点注册 `SIGTERM`/`SIGINT`，handler 只设置停止标志，主循环在最短周期内进入统一 `safe_shutdown()`；避免在 signal handler 内执行复杂日志和资源操作。
2. 把“左右回中、结果检查、可选 disable、状态上报”收敛为单一方法，由 command timeout、input watchdog、异常退出和正常退出复用。
3. 左右通道分别记录写入结果；任一失败即进入 fault，尝试双路安全输出，发布明确通道/错误，不再发布期望值作为硬件事实。
4. Runtime 保留当前 `SIGTERM → 等待 → SIGKILL` 结构；先通过节点安全退出完成 A1，不先重写 launcher 协议。若目标机证明等待窗口不足，再单独调整。
5. 硬件侧确认并验证电机控制器的输入信号超时、使能脚、安全继电器或独立断电回路。`SIGKILL`、CPU 死机、系统掉电不由 Python 清理承诺。

**需要评审的选择**

- 安全状态仅“输出中位”，还是“中位后 `enable=0`”；
- `enable=0` 后重启节点的重新初始化流程；
- 单侧回中失败时是否立即 `sdk.die`，以及在 die 前允许的重试次数；
- 硬件控制器是否已有可靠信号丢失保护，实测延迟是多少。

**自动化与故障注入**

- Fake sysfs：正常双路写、左失败、右失败、双失败；
- 子进程在非零输出后收到 `SIGTERM`，最后成功写值必须是安全值；
- 主循环异常、input watchdog、command timeout 复用同一安全方法；
- 失败路径不得发布“正常/已停止”状态；
- Runtime 多轮 start/stop 后无 PWM 节点残留。

**台架与现场验收**

- 目标 Orange Pi 上确认 pwmchip/channel、左右履带和中值；
- 电机离地，依次测试 stop-dataflow、stop runtime、kill PWM 节点、Agent/runtime 重启；
- 独立验证信号线断开、`SIGKILL`、系统掉电时的硬件保护；
- 记录每种路径的回中/断能延迟，不只记录“看起来停了”；
- 最低速度、空旷区域、操作员 + 安全员共同确认后才允许 Go。

**回滚**

代码回滚即同时恢复 `dry_run_mode: true`；已增加并验证的硬件失效保护不得随软件回滚移除。

**Go 条件**

- 所有可调度退出路径双路进入安全状态；
- 任一 I/O 失败可观察、不会伪报成功；
- 不可调度故障由独立硬件保护给出实测证据；
- 板型、通道、中值和左右映射已冻结记录。

### WP-A2：RTK 航向有效期与降级规则

**目标**

- THS/GPHDT 无效或停止后，不再无限复用旧航向；
- 不产生“时间新鲜但航向陈旧”的 pose；
- 低速车辆不默认把噪声较大的 RMC ground track 当作可靠车头航向。

**非目标、依赖与评审**

- 非目标：本包不引入 IMU/EKF，也不重写定位框架；
- 依赖：UM982 原始日志、报文频率、THS 状态语义和低速 ground track 误差；
- 必须评审：RTK/定位、控制、测试、现场操作员。

**推荐候选方案**

1. 在 parser/driver 中保存 `heading_source`、`heading_valid` 和本地单调接收时间；
2. 无效 THS 立即使 device heading 失效，超过配置时限自动失效；
3. `heading_source=device` 时，无可靠设备航向默认 fail-closed：不向控制链伪装有效 heading；
4. RMC ground-track fallback 仅作为可选配置，并同时满足 RMC 状态有效、速度高于经现场确认的阈值；停车和低速转向时不启用；
5. 把来源切换、失效和恢复写入结构化日志/状态，便于现场复盘。

**待评审参数**

- UM982 THS/GPHDT 实际频率与无效状态语义；
- 航向最大允许年龄，建议不大于控制 pose freshness 的 0.5 秒，但最终值由实测确定；
- 是否允许 ground-track fallback，以及最低速度；
- 无航向时是停止输出 pose，还是显式输出 invalid 并由下游停车。

**验收**

- 有效 THS → 无效 THS → 相反 RMC，不得继续输出旧 THS；
- THS 静默超时、恢复、乱序和频率下降；
- 静止、低速转向、直线行驶下验证 fallback；
- 下游在规定时间内输出零速度/安全状态；
- 目标 UM982 原始日志回放通过后再做 dry-run 现场采样。

**回滚与 Go 条件**

回滚时保持 dry-run；不得把“继续沿用旧航向”作为实车降级。所有失效序列不再产生新鲜时间戳包装的旧航向，才允许 Go。

### WP-A3：规划热更新的请求所有权与切换安全

**目标**

- 正在发布旧路径时收到更新，至少保留最新一份并最终处理；
- `plan_revision` 和内容变化有明确契约；
- 路径切换期间不继续以旧目标驱动车辆。

**非目标、依赖与评审**

- 非目标：本包不实现行驶中的无缝抢占、多版本队列或通用工作流；
- 依赖：revision 生产规则和 SAFE-01 的可确认停车路径；
- 必须评审：规划、控制、Agent/Cloud、现场操作员。

**推荐候选方案**

1. 内层循环读到更新时保存为 `pending_request`，退出旧发送循环后立即处理；
2. 沿用 latest-value 单槽语义：连续更新只保留最新一份，不引入队列平台；
3. 正常生产者每次内容变化必须递增 `plan_revision`；planner 同时计算内容 fingerprint 作为安全网，相同 revision 但内容变化时告警并按评审结果重规划或拒绝；
4. 首个实车版本**不承诺运行中无缝切换**：流程固定为 `stop-dataflow → 确认 runtime 已停且 PWM 安全 → 更新计划 → restart-dataflow`；`pending_request` 修复先在 dry-run 验证其不丢请求；
5. Web 保存、Agent 任务生成和 planner 使用同一 revision 契约。

未来如果确实需要行驶中切换，必须另行设计 `path_invalid/hold` 信号、控制端停车确认和超时；不能仅凭 planner 保存了 `pending_request` 就宣称切换期间已经停车。

**验收**

- 旧路径发送中注入一次和连续多次更新；
- 同 ID 新 revision、同 revision 内容变化、跨地块切换；
- 证明每个合法的最后请求最终被处理一次；
- 实车流程中 stop-dataflow 已确认、PWM 已进入安全状态后才允许写入新计划并重启；
- dry-run 中旧路径停止刷新，新路径完整输出；
- 首次现场只在停车状态验证。

**临时回避与 Go 条件**

方案未通过时，操作规程强制“停止当前任务 → 确认 PWM 中位 → 重新下发”，禁用热更新。首版 Go 只代表停车换任务路径和 dry-run 请求所有权通过，不代表已批准行驶中无缝切换。

## 5. 阶段 B：L2 云边任务闭环

### WP-B1：动态任务资产路径契约

**目标**

- Agent 产生的 parcel 能被真实 planner 读取；
- 不依赖对 `/opt/nodeflow` 代码目录的写权限。

**非目标、依赖与评审**

- 非目标：本包不处理 MQTT 回调线程模型，不建设通用资产平台；
- 依赖：部署用户、运行数据根权限和 planner 参数契约；
- 必须评审：Agent、规划、部署、测试。

**两个候选路径方案**

| 方案 | 优点 | 缺点 | 建议 |
|---|---|---|---|
| 直接把旧 `node-hub` 改为当前包目录 | 改动最小 | 仍向代码树写运行数据；只读部署易失败 | 仅可作为短期止血，不作为首选 |
| 独立 task data root，planner 接收明确的 `parcel_file`/`parcel_dir` | 适合 `/var/lib/nodeflow`，权限和清理边界清楚 | 需要 Agent 与 planner 增加一个小契约 | **推荐评审** |

推荐候选为 `NODEFLOW_TASK_DATA_ROOT`（最终名称待评审）下的 task 作用域目录，由 Agent 原子写入并通过 node params 把具体文件传给 planner；静态示例 parcel 仍可保留在包内。

**验收**

- 临时只读代码树 + 可写 task data root；
- 下载后由真实 `load_parcel_config`/parcel planner 消费，不只断言文件存在；
- 同一 task 重投保持幂等，不产生半写文件；
- L2 最小地块从下发到生成 global path 的集成测试通过。

**回滚与 Go 条件**

回滚时禁用动态资产，改为人工预置 parcel，并明确 L2 dynamic parcel 不可用。代码树只读时真实 planner 能消费 Agent 生成的资产，才允许 Go。

### WP-B2：Agent 绑定当前 run 与完成契约

**目标**

- Agent 与 runtime 分进程时仍能读取当前 run 的进度和完成数据；
- runtime 创建新 run 后，不读取上一轮 stale buffer；
- 不再要求所有 preset 都必须包含 waypoint/pose/velocity/tillage 这一组固定节点。

**非目标、依赖与评审**

- 非目标：不恢复全局 buffer，也不长期维护新旧双目录；
- 依赖：固定控制面的 current run 契约，以及任务/preset 的完成契约；
- 必须评审：Runtime/SDK、Agent、Cloud/产品、测试。

**推荐候选方案**

1. 把当前 CLI 的 run 目录定位逻辑下沉为 runtime 公共 helper，不让 Agent 导入 CLI；
2. TaskExecutor dispatch 后从固定控制面 `runtime.status`/PID 元数据取得 `run_id`，显式绑定 `<runtime_root>/runs/<run_id>/buffers`；
3. 每个监控周期验证 active run 是否仍匹配；变化时进入 interrupted/reconcile，不静默回落固定根目录；
4. `SharedBufferLite` 增加可显式传入目录的使用方式，避免修改整个 Agent 进程的全局环境；
5. 完成判定记录使用的 run_id，供日志和云端诊断；
6. preset 明确声明 completion contract；未声明时不得套用耕作节点条件，可选择人工终结或拒绝 L2 自动执行。

**验收**

- Agent/runtime 独立进程集成测试；
- task 启动前后 run_id 变化；
- runtime 重启后旧 buffer 中即使存在 completed 数据也不能误判；
- 正常任务能上报 progress、进入 COMPLETED 并触发下一步骤；
- 无 active run 时明确失败或等待，不回落猜测目录；
- 耕作 preset 与不含 tillage/waypoint 的最小 preset 分别验证完成语义。

**回滚与 Go 条件**

回滚时关闭 L2 自动完成，使用人工确认；不得恢复“猜测两个目录”或继续硬编码更多节点名。跨进程、新 run 和两类 preset 均通过才允许 Go。

### WP-B3：Agent 重启、取消与状态对账

**目标**

- 重启后不出现 `online + machine_busy`；
- 不自动恢复可能产生运动的任务；
- cancel 失联后有明确、保守的状态，而不是永久悬挂或伪报 cancelled。

**非目标、依赖与评审**

- 非目标：不实现任意时刻无缝续跑或分布式事务；
- 依赖：runtime 暴露可核对的 `active_task_id`/停止确认，Cloud 接受评审后的中断状态；
- 必须评审：Agent、Cloud、Runtime、控制、安全、现场操作员。

**推荐候选方案**

1. Agent 启动进入 `recovering`，扫描本地非终态任务并读取 runtime.status；
2. 只有当 `runtime.status.active_task_id` 与遗留 task_id 匹配时，才自动请求 stop-dataflow；若 runtime 正在运行另一个手工/L1 数据流，进入 conflict 并要求人工确认，不得误停无关任务；
3. stop 命令必须等待同一 task_id 的 `dataflow_running=false/stopped` 确认；确认前不得标 `CANCELLED`，超时进入 `cancel_unconfirmed` 或等价状态；
4. 能确认 runtime 未执行时，把任务置为 `interrupted`/`failed` 并上报；无法确认停止时置为 `communication_lost`/`cancel_unconfirmed`，要求人工确认；
5. 心跳从对账状态、store 和 runtime 综合生成，不只依赖新 executor 的 current_task_id；
6. 云端 cancel 达到重试上限后进入明确的非成功终态，不释放为“已安全取消”；
7. Agent 收到未知 cancel 时回送 `unknown_task`/`cancel_unconfirmed` ACK，帮助云端收敛。

**必须评审的状态语义**

- 是否新增 `interrupted`、`cancel_unconfirmed`，还是复用现有 `communication_lost/failed`；
- 哪些状态允许云端自动重试；
- 同一地块在执行状态未知时是否禁止重新分配；
- 操作员如何确认车辆已停并解除任务占用。

**验收**

- 分别在 PENDING、DOWNLOADING、READY、RUNNING、cancel_requested 时杀死并重启 Agent；
- Agent 重启而 runtime 运行同 task、不同 task 和手工 L1 数据流三种情况；
- cancel 只有收到同 task_id 的停止确认才进入成功终态；
- 长于重试窗口的 WiFi 断线、未知 cancel、重复 dispatch；
- 最终状态可解释、不会永久占用、不会重复执行。

**回滚与 Go 条件**

回滚时关闭 L2 Agent，人工确认 runtime 已停并清理任务状态后才能重新启用。所有非终态重启场景都有确定且不误停无关图的结果，才允许 Go。

### WP-B4：SQLite 心跳时间与离线转移

**目标**

- SQLite 下不再出现 aware/naive datetime 异常；
- 机器离线时所有与该机器绑定的非终态任务都有评审过的转移规则。

**非目标、依赖与评审**

- 非目标：不迁移 PostgreSQL，不实现通用租约服务；
- 依赖：Cloud/Agent 状态转换表和现场 heartbeat 超时阈值；
- 必须评审：Cloud、Agent、测试、现场操作员。

**推荐候选方案**

1. 增加单一 UTC 归一化 helper；SQLite 读出的 naive 时间按已约定的 UTC 解释，再参与比较；
2. 不为此迁移 PostgreSQL，也不引入租约服务；
3. 用真实临时 SQLite 做集成测试，不只 mock datetime；
4. 状态表覆盖 DOWNLOADING、READY、RUNNING、cancel_requested 等，不只现有两个状态；
5. 恢复心跳只恢复通信状态，不自动恢复车辆动作。

**验收**

- 未超时、临界值、已超时、重复检查和重新上线；
- 断开车辆 WiFi，在规定阈值内 UI 显示 offline；
- 活动任务进入预期状态，数据库无异常循环日志；
- 重连后不产生自动续跑或重复 dispatch。

**回滚与 Go 条件**

回滚时停用 L2 自动调度并使用人工离线确认。真实 SQLite、多种活动状态和掉线恢复都收敛后才允许 Go。

### WP-B5：MQTT 初始连接恢复与服务健康

**目标**

- Cloud 先启动、broker 后启动时无需人工重启；
- HTTP 存活与 MQTT 可用状态明确区分。

**非目标、依赖与评审**

- 非目标：不更换 MQTT 库，不建设 broker 集群或新 supervisor；
- 依赖：Cloud Box 服务顺序、health 契约和现有订阅恢复逻辑；
- 必须评审：Cloud、部署、测试。

**推荐候选方案**

1. 复用 paho 的异步/重连能力或在现有服务内增加受控初连重试；
2. 初连失败时服务状态为 degraded，使用有上限的指数退避，不阻塞 HTTP；
3. 成功连接后沿用现有重订阅逻辑；
4. health/status 暴露 `mqtt_connected`、最近错误和最近成功时间；
5. systemd 启动顺序可作为辅助，但不能是唯一恢复机制。

**验收**

- Cloud 先启动、broker 后启动；
- broker 先启动、Cloud 后启动；
- broker 运行中重启；
- WiFi 短断恢复；
- 恢复后不重复执行已 ACK 任务。

**回滚与 Go 条件**

回滚时保持服务 degraded 并由 systemd/人工重启，L2 不放行。三种启动顺序和运行中重启均自动恢复后才允许 Go。

### WP-B6：MQTT 回调与资产下载解耦

**定位：条件性可靠性工作包，不阻塞最小 L2 功能闭环。**

**目标**

- Cloud HTTP 不可达或大资产下载时，MQTT keepalive、cancel 和其他回调仍能处理。

**非目标、依赖与评审**

- 非目标：不引入 Celery、通用任务队列或多任务并发；
- 依赖：B1 资产路径、B3 cancel 状态和现场最大资产规模/网络超时；
- 必须评审：Agent、Cloud、测试；如果现场证明确认所有资产都小且下载上限足够，也可决定暂缓。

**推荐候选方案**

MQTT 回调只做校验、持久化和 ACK；容量为 1 的受控 worker 执行下载。车辆仍只接受一个活动任务。worker 必须响应 cancel，Agent 停止时可等待或将任务转为 interrupted。

**验收、回滚与 Go 条件**

- 慢下载、HTTP 超时、下载中 cancel、Agent 重启；
- MQTT keepalive 和 cancel 延迟保持在评审阈值内；
- 回滚时恢复同步下载并记录资产大小/超时限制；
- 本包只有在现场资产和网络条件触发时才成为 L2 Go 前置条件。

**L2 总体 Go 条件**

WP-B1～B5 全部达到 Go，并完成一次真实 Cloud Box + Edge 的最小闭环：下发地块 → 下载 → planner 读取 → runtime 执行 → progress → 安全完成 → 云端终态。只修其中一两项不能宣称 L2 已可用。WP-B6 是否成为放行前置，由实际资产规模、下载超时和 WiFi 故障测试决定。

## 6. 阶段 C：部署、CLI 与测试可信度

### WP-C1：目标机安装、依赖与收车命令

**目标、非目标、依赖与评审**

- 目标：干净目标机按仓库脚本可启动、停止并被操作员可靠确认已停；
- 非目标：不 Docker 化，也不重做 Python 打包体系；
- 依赖：实际 Orange Pi 板型、Python 3.12 镜像、service user 和运行目录权限；
- 必须评审：部署、Runtime、硬件、测试、现场操作员。

**建议改动**

- systemd 模块改为 `edge.runtime.main` 与 `edge.agent.agent_main`；
- 节点依赖扫描根改为 `edge/nodes`；
- 安装结束执行 import、`--help`、runtime idle status 和服务启动 smoke；
- 固定并记录 Python 3.12、目标 Linux 镜像和 service user 权限；
- 更新部署文档中的旧模块路径，但不顺带重写全部 docs 索引；
- 收车流程优先使用 NodeFlow CLI 的 stop/status；如保留 `pkill` 作为救援手段，必须匹配当前 `edge.*` 模块并在随后检查 PID/进程与 PWM 安全状态。

**验收**

- 干净 Python 3.12 环境完整安装，无开发机残留包；
- systemd start/stop/restart/开机顺序；
- 目标 Orange Pi 重复一次；
- 代码目录只读、运行数据目录可写；
- 服务失败时日志明确，不出现脚本误报“安装完成”；
- 现场文档中的停止命令能终止当前模块，并由 status/进程检查证明已停。

**回滚与 Go 条件**

回滚时改为经过验证的人工启动/停止清单并保持 dry-run。干净目标机无需手工补包、收车命令可验证后才允许 Go。

### WP-C2：离线 CLI 任务生命周期

**目标、非目标、依赖与评审**

- 目标：所有公开模式都有一个仍存活的 owner 推进任务状态；
- 非目标：不新增常驻调度服务；
- 依赖：B2 的 run/完成契约和实际使用者对前台/Detached 的选择；
- 必须评审：CLI、Runtime、Agent、测试、使用者。

当前需要产品选择，不宜直接写代码：

| 选择 | 行为 | 代价 |
|---|---|---|
| 前台等待终态 | CLI 进程承担监控，退出码明确 | 长任务占用终端 |
| Detached 只交给持久 Agent | CLI 只请求 Agent，生命周期有常驻 owner | 依赖 Agent，不能称纯离线 |
| 降级为 dispatch-only | 最小改动，文档诚实 | 不再提供完整 task 生命周期 |

推荐组合：默认前台等待；需要 detached 时只允许交给持久 Agent。CLI 自己不创建“退出即消失”的后台 daemon monitor。

**验收**

- 正常完成、Ctrl-C、cancel、runtime 中断；
- CLI 退出后不存在无人维护但仍宣称自动监控的 RUNNING 任务；
- 完成条件按任务类型定义，不只硬编码 tillage/waypoint 数据。

**回滚与 Go 条件**

未定案时暂停宣传 offline `task run` 的完整生命周期，使用 runtime/Agent 明确操作。所有公开模式都有存活 owner 后才允许 Go。

### WP-C3：图输入唯一性与配置修复

**目标、非目标、依赖与评审**

- 目标：普通单输入端口不会静默选择多个上游中的第一条；
- 非目标：本包不设计通用 merge 节点或消息总线；
- 依赖：确认 `tillage_operation` 中 task_enu 的唯一权威来源；
- 必须评审：Runtime/graph、规划、机具控制、测试。

**建议改动**

1. Graph validator 拒绝普通单输入端口的多个上游；如未来需要 merge，必须显式声明 merge 语义；
2. 修复 `tillage_operation.yaml` 的双来源冲突并确认正确的 task_enu 所有者。

**验收、回滚与 Go 条件**

- graph validator 对多来源输入给出包含节点/端口/两来源的明确错误；
- 修复后的 tillage 图接收到评审确认的边界/参考点；
- 回滚时不运行该图的自动 zone 判断；
- 所有现有 graph 均通过唯一性检查后才允许 Go。

### WP-C4：CI 与测试可信度

**目标、非目标、依赖与评审**

- 目标：有效测试进入 CI，错误必须以非零结果表现；
- 非目标：不一次性恢复全部历史 MCP/simulation/legacy，也不把硬件测试塞入普通 CI；
- 依赖：当前有效测试清单、Linux runner 和可接受运行时间；
- 必须评审：测试，以及 Runtime、Cloud、Agent、规划各模块负责人。

**建议改动**

1. CI 纳入当前稳定的 quick、integration、edge nodes；preflight 作为显式 Linux job；
2. 修复“捕获异常后 return False”类假绿；
3. 旧 MCP/simulation/legacy 测试逐项标为迁移、明确 skip 或删除，不假装属于当前覆盖；
4. CI 固定 Python 3.12，3.14 只作为附加兼容结果；
5. 为本轮每个工作包增加跨模块回归，而不是只测私有 helper。

**验收、回滚与 Go 条件**

- 人为注入一个预期错误，CI 必须非零失败；
- 本地与 CI 收集数量有文档记录；
- preflight 后 runtime、buffers、5555/8080 和进程全部清理；
- 安全与 L2 问题至少各有一个真实跨进程或真实 SQLite 测试；
- 新增 job 若临时非阻断，必须记录负责人和恢复阻断的期限；不得删除既有阻断测试。

## 7. 阶段 D：真实机具控制，单独立项

### WP-D1：implement driver、反馈与输入老化

该工作包不与 A/B/C 阶段并行实施真实硬件输出。开始前必须已有明确的机具接口清单。

**目标、非目标、依赖与评审**

- 目标：把逻辑命令映射到已确认的硬件接口，并区分命令与物理完成；
- 非目标：无传感器时不声称闭环耕深，不在接口未知时编写猜测性驱动；
- 依赖：WP-A1、真实执行器/继电器/CAN/485 和反馈清单；
- 必须评审：机具、控制、硬件/电气、测试、操作员、安全负责人。

**候选范围**

- 形成 PTO、悬挂、电液压推杆的输出方式、有效电平、故障状态和急停关系说明；
- 增加独立 implement driver，不让 tillage controller 直接操作硬件；
- 增加 pose/progress/task 输入年龄检查，超时输出 PTO OFF、悬挂安全状态或由硬件负责人定义的安全值；
- 有反馈时区分 command_sent、actuating、physical_completed、fault；
- 无反馈时只允许 command_sent/operator_confirmed，不自动标 physical_completed；
- 增加 implement feedback 和底盘/机具安全仲裁前，禁止无人值守。

**验证顺序**

Fake driver → 继电器/执行器离机台架 → 空载升降/PTO → 断流/节点退出 → 最低速带机具现场测试。

**Go 条件**

硬件接口、输入超时、安全值、反馈语义和急停行为全部有实测证据；否则保持逻辑输出和人工机具操作。

**回滚**

完全禁用 implement driver，保留逻辑输出和人工机具操作；不得把无反馈的旧状态解释为物理完成。

## 9. 提交边界与回滚规则

### 9.1 建议提交边界

- A1、A2、A3 分为三个独立提交/PR；
- B1、B2、B3、B4、B5、B6 分开，B2/B3 可在同一评审周期但不混为一个提交；
- C1、C2、C3、C4 分开；
- D1 单独项目，不与底盘或 L2 修复混合；
- 每个提交同时包含对应的回归测试和必要文档，不接受“先改代码以后补测试”。

### 9.2 通用回滚规则

1. 实车相关工作包回滚后，立即恢复 dry-run，不继续真实输出；
2. L2 工作包回滚后，关闭自动下发或改为人工预置/人工确认，不保留半新半旧双路径；
3. 状态机变更必须提供数据库/本地 TaskStore 的向后处理策略；
4. 不删除事故日志、原始 RTK 记录或失败测试证据；
5. 硬件安全改进原则上不随软件版本回滚；
6. 出现无法解释的运动或状态时，优先停止和保留现场，不自动重试。

| Gate | 条件 | 允许进入 |
|---|---|---|
| **Gate A：事实冻结** | 审计编号、复现、硬件条件经负责人确认 | 方案定稿 |
| **Gate B：逐包设计批准** | 任一工作包编码前，均须由该包列明的角色批准；A1～A3 额外要求 Runtime、控制/RTK、硬件、安全联合批准 | 对应工作包编码 |
| **Gate C：逐包自动化通过** | 对应包的单测、集成、故障注入和目标 Python/Linux 通过 | 对应功能的目标板 dry-run |
| **Gate D：台架通过** | 电机离地/执行器离机验证，急停可用 | 限定低速实车 |
| **Gate E：L1 放行** | A1、A2 通过；允许运行中更新时再要求 A3；现场操作规程冻结 | 有人监管 L1 |
| **Gate F：L2 软件闭环** | B1～B5 + C1/C3/C4 在 dry-run 完成真实云边闭环；B6 按网络/资产条件决定 | L2 dry-run 联动 |
| **Gate G：真实车辆 L2** | Gate E 与 Gate F 累计通过 | 有人监管的真实车辆 L2 |
| **Gate H：机具放行** | Gate G 与 D1 软硬件反馈、安全验收累计通过 | 真实 PTO/悬挂 |

任何 Gate 出现以下现象直接 No-Go：

- 任一通道保持无法解释的输出；
- 位置新鲜但航向陈旧；
- 更新已确认但仍沿旧路径；
- Agent/runtime/cloud 对同一任务给出互相矛盾的活动状态；
- cancel 被显示为成功但车辆执行状态未知；
- 测试依赖开发机残留环境或通过吞异常得到绿色结果。
