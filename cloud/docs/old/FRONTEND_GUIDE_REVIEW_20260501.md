# NodeFlow 云端前端界面设计评审意见

> 评审对象: `cloud/docs/FRONTEND_GUIDE.md`
> 评审日期: 2026-05-01
> 目标: 从“农场作业管理后台是否好用、是否适合长期扩展”的角度给出改进建议

---

## 总体判断

这版前端设计的方向是对的。

如果把目标产品理解成“农场设备调度 + 作业执行 + 地块管理”的云端控制台，那么当前方案已经具备一个合理的骨架:

- 地图是默认落点，符合农业场景
- 机器、作业、地块三条主线清晰
- 创建作业采用 3 步向导，适合低频但高价值操作
- 作业详情承担执行期监控，职责也比较自然

从产品气质上看，它确实比传统 CRUD 后台更接近你说的“模拟农场 25”那类管理界面思路: 不是纯表单系统，而是“地图 + 设备 + 作业流”的操作面板。

但当前文档和实现仍然更偏“管理后台”，还没有完全进入“作业指挥台”模式。最主要的问题不是界面不好看，而是:

- 信息层级还不够偏向“当前正在发生什么”
- 地图和作业执行之间的联动还不够强
- 若以后机器数、任务数、地块数增加，当前布局会开始吃力

---

## 优点

### 1. 信息架构是合理的

当前导航结构:

- 地图
- 机器
- 作业
- 设置

这四类基本覆盖了农业云端平台最核心的管理对象，学习成本低，也方便后期继续扩展“地块资产”和“执行过程”两个层面。

其中最正确的一点，是把 `FarmMapView` 放成默认着陆页，而不是把 `/jobs` 列表作为首页。

农业类系统的第一视角通常应该是:

- 设备在哪
- 地块在哪
- 哪块地正在执行

而不是:

- 表格里有哪些记录

这点方向上是加分项。

### 2. 创建作业的 3 步向导很适合当前阶段

`JobCreateView` 的设计把复杂动作拆成:

1. 选地块与步骤
2. 做分割与分配
3. 最终确认并下发

这个流程符合实际业务认知顺序，比单页大表单更好，也比过度自动化更稳。

尤其是“先预览分割，再分配机器”这个动作顺序是对的，能让操作员先建立空间认知，再做资源决策。

### 3. 地图承担了真实业务含义，而不是装饰

文档里地图不是一个只负责展示底图的背景组件，而是承担了:

- 地块选择
- 手绘地块
- 分割预览
- 机器位置显示

这说明产品思路不是“后台加个地图”，而是“地图本身就是业务主画布”。这一点很重要，也是未来能做出行业感的基础。

---

## 主要问题

### 1. 首页还不够像“作业指挥台”

目前 `FRONTEND_GUIDE.md` 里的首页仍然是“地图 + 地块侧栏”的思路。

这对地块资产管理是好的，但对“当前农场正在发生什么”表达不够强。

如果参考你提到的“模拟农场类管理界面”气质，首页应该更强调:

- 当前正在执行的作业
- 哪台机器在忙
- 哪块地正在跑
- 是否存在离线、失败、卡住的异常

也就是说，首页除了地块列表，更需要一层“运营总览条”。

建议增加首页顶部总览区，至少包括:

- 今日作业数
- 运行中作业数
- 在线机器数
- 异常机器数
- 当前覆盖面积/完成率

这样首页就会从“地图页”升级为“农场控制中心”。

### 2. 地图和作业详情的联动还不够强

现在的说明里，地图页和作业页是分开的。

这没有错，但如果你想往“沉浸式管理界面”靠，建议加强联动:

- 在地图上点击机器，可联动跳到对应任务/作业
- 在作业详情点击某个 step 或 task，可高亮对应地块/子地块
- 在地图上直接看到“当前作业归属”的视觉编码

目前文档中的分割预览更多是“创建时的静态预览”，而不是“执行时的动态态势图”。

建议后续把地图从“创建阶段工具”升级成“执行阶段总览面板”。

### 3. 地图缩放层级应该驱动展示重点切换

这是一个很重要的方向，我认为应该明确写进设计原则里:

- 地图缩放级别不是纯视觉操作
- 它应该直接决定“当前用户最该看什么”

也就是说，地图不应该在所有缩放层级都同时展示:

- 地块边界
- 子地块
- 机器 marker
- 机器状态
- 作业进度
- 任务标签

这样会导致两种坏结果:

- 远景时信息爆炸，整张图很吵
- 近景时真正重要的细节又不够突出

建议把地图拆成三个层级模式。

#### A. 总览层级

适用场景:

- 一屏能看到多块地
- 用户在做全局巡视

此时地图应重点回答:

- 哪些地块在执行
- 哪些地块已完成
- 哪些地块异常
- 哪些地块待执行

建议展示:

- 地块轮廓
- 地块或子地块的作业进度着色
- 地块级状态标签，例如 `待执行 / 进行中 / 完成 / 异常`
- 当前作业的覆盖热度或完成百分比

建议省略或弱化:

- 单台农机的细粒度状态
- 机器 CPU、内存、心跳等技术指标
- 机器 task_id 文本

原因:

- 当用户在总览层级时，真正关心的是“哪块地出了问题”，不是“哪台机器 CPU 多少”

#### B. 作业层级

适用场景:

- 地图缩放到 1 块地或 1 个作业区域附近
- 用户正在关注某一个作业

此时地图应重点回答:

- 当前作业分成了哪些子任务
- 每个 split 的进度和状态如何
- 哪台机器负责哪个区域

建议展示:

- 子地块分割边界
- 按作业或 step 着色的 split
- 机器与 split 的归属关系
- step 级或 split 级进度

建议弱化:

- 其他无关地块的细节
- 全局告警信息

这个层级是“总览”和“设备近景”之间的过渡层，也是最有农业业务特色的一层。

#### C. 设备层级

适用场景:

- 用户继续放大，进入单机作业观察
- 用户点击某台机器进行定位

此时地图应重点回答:

- 这台机器当前状态是什么
- 它是否在线、忙碌、异常
- 它正在执行哪一段任务
- 它相对地块边界和路径的位置如何

建议展示:

- 机器 marker 的强化样式
- 机器状态图标
- 当前 task 或 step 简述
- 行驶方向、当前位置、最近轨迹

建议省略:

- 其他远处地块的复杂状态标签
- 大量地块级统计文本

这个层级才是展示“机器状态”的最佳时机，而不是在全图总览时把机器细节全部摊开。

#### 建议的交互规则

建议把缩放和信息密度做成明确规则，而不是依赖开发阶段临时判断:

1. 当地图处于远景时:
   - 隐藏机器文字标签
   - 只保留必要 marker，或者合并为聚合点
   - 强调地块/作业进度色块

2. 当地图放大到作业层级时:
   - 展示 split 边界
   - 展示机器与 split 的绑定关系
   - 显示 step 或作业状态

3. 当地图放大到设备层级时:
   - 展示机器详细状态
   - 显示定位、路径、当前任务摘要
   - 地块信息退居次要层

#### 建议的视觉优先级

可以把这条原则总结为:

- 远景看“地”
- 中景看“作业”
- 近景看“机”

这条规则非常适合农业云端平台，也和你提到的那类管理界面思路一致。

如果后续真做这个设计，地图体验会从“很多图层叠在一起”变成“视角切换后信息自动聚焦”，整体专业感会强很多。

### 4. 当前页面结构在多任务并发时会开始拥挤

当前设计适合:

- 少量机器
- 少量地块
- 少量同时运行作业

但一旦进入“多机、多块、多步骤并发”的真实调度场景，现有页面会出现几个问题:

- `MachineDashboard` 会变成卡片海
- `JobListView` 只剩表格检索感，缺少优先级信息
- `JobDetailView` 的 timeline 对单作业很好，但对多作业并发没有全局视角

建议后续增加一个更偏运营态的总览页，或者把首页增强为运营总览，而不是完全依赖:

- `/machines`
- `/jobs`

这两个二级页面分别查看。

### 5. “设置页”在当前产品阶段偏弱

`SettingsView` 现在承载的是:

- MQTT 只读配置
- 手动注册机器
- 农场参考点

这几项是有用的，但产品价值感不强，也不够像一个真正会被频繁使用的业务页面。

从农业运营后台角度看，设置页通常不是高频入口，当前内容也偏“系统参数展示”。

建议考虑两种方向:

- 方向 A: 继续保留，但降权，不必放在主导航这么显眼的位置
- 方向 B: 扩充成“系统与设备中心”，增加机器模板、默认作业参数、地图底图设置、告警阈值等

否则它会显得像一个功能尚未长成的占位页。

## 与当前实现的落差

这部分不是在否定设计，而是提醒: 文档已经比现状实现更完整了，后续要小心“文档先于产品现实太多”。

### 1. `JobTimeline` 当前实现还支撑不起文档里的理想效果

文档里 `JobDetailView` 表示 timeline 能按 step 展示对应 task。

但当前实现中的 `tasksForStep()` 实际上没有正确按 step 过滤任务，几乎会把所有 task 都挂到每个 step 下面，逻辑明显还只是占位状态。

参考实现:

- `cloud/web/src/components/job/JobTimeline.vue`

这意味着文档里的“Step 下属 task 可视化”方向是好的，但实现层需要尽快补齐，不然会影响用户对时间线的信任感。

### 2. 地图缩放驱动展示切换目前还没有实现基础

我上面提的“远景看地、中景看作业、近景看机”，当前实现里还没有明显的技术基础。

例如当前 `MachineMarker` 是简单的 `watch(machines) -> renderMarkers()`，没有看到:

- 基于 `zoom` 的 marker 显隐策略
- marker 聚合
- 地块状态图层与机器图层的层级切换
- 由地图缩放触发的信息密度变化

参考实现:

- `cloud/web/src/components/map/MachineMarker.vue`
- `cloud/web/src/components/map/FarmMap.vue`

所以这块如果要落地，建议后续在地图容器层统一管理:

- 当前 zoom level
- 当前 focus mode
- 当前图层策略

不要把逻辑分散到每个图层组件自己决定。

### 3. 顶栏信息还太少

文档里的整体气质偏“管理中心”，但当前 `TopBar` 只显示:

- 标题
- 在线数
- 离线数

缺少:

- 忙碌数
- 当前运行作业
- 告警入口
- 最近失败任务提示

参考实现:

- `cloud/web/src/components/layout/TopBar.vue`

如果你想靠近“模拟农场式管理界面”的感觉，顶栏至少应承担全局态势入口，而不是单纯页头。

### 4. 机器卡片信息有基础，但还不够“调度可用”

当前 `MachineCard` 展示了:

- 类型
- CPU
- 内存
- 运行时长
- 心跳
- 当前 task

这对技术调试很好，但对调度员来说还缺两类信息:

- 它属于哪个作业/哪块地
- 它现在能不能被再次分配

参考实现:

- `cloud/web/src/components/machine/MachineCard.vue`

建议后续把“技术指标”和“业务状态”拆层展示，避免卡片信息太偏工程监控。

### 5. 地图上的机器标记太弱

当前 `MachineMarker` 是圆点 + tooltip 模式，适合 demo，但还不够像实际作业调度界面。

参考实现:

- `cloud/web/src/components/map/MachineMarker.vue`

建议以后考虑:

- 机器朝向
- 作业状态图标
- 所属作业颜色
- 点击后弹出任务摘要

农业场景里，地图上的设备不是简单 marker，而是最重要的操作实体之一。

## 我建议你往哪个方向收敛

如果你觉得“模拟农场 25 那种管理界面”合适，我是赞同的，但不要直接学它的视觉皮肤，而是学它的几个核心原则:

### 1. 强调“世界状态”，弱化“表单后台感”

优先展示:

- 机器在做什么
- 地块发生了什么
- 作业推进到哪一步

而不是优先展示:

- 配置项
- 参数列表
- 管理表格

### 2. 默认视角应该偏“现场态势”

首页可以继续是地图，但建议升级成:

- 顶部运营摘要
- 中间地图主视图
- 右侧当前作业与异常列表

而不是单纯“地块列表 + 新建作业按钮”。

### 3. 所有对象都要能互相跳转

一个成熟的农场管理界面，用户点任何一个对象，都应该能快速走到关联对象:

- 机器 → 当前任务 → 所属作业 → 所在地块
- 地块 → 历史作业 → 当前任务 → 分配机器
- 作业 → 子任务 → 机器 → 地图定位

当前文档中的流转已经有雏形，但还可以做得更明显。

### 4. 把“异常”做成一等公民

农业场景里最有价值的信息不是“都正常”，而是:

- 哪台机器离线了
- 哪个任务卡住了
- 哪个作业失败了
- 哪块地迟迟没推进

建议后续设计里加入:

- 告警角标
- 异常列表
- 失败任务快捷重试入口
- 离线机器聚合卡片

这样产品才会从“可管理”升级到“可运维”。

## 具体建议

### 建议 1: 首页升级为“农场运行总览”

保留地图为中心，但增加三层结构:

- 顶部: 今日作业、运行中、异常、在线机器
- 中间: 地图
- 右侧: 当前作业/待处理告警/最近事件

### 建议 2: `JobDetailView` 加强地图联动

建议支持:

- 点击 step 高亮相关 split
- 点击 task 定位对应机器
- 当前 step 在地图上高亮显示

### 建议 3: 把“缩放驱动展示切换”写成正式设计约束

建议直接落成一条设计规范:

- `zoom-out` 时优先展示地块作业状态
- `mid-zoom` 时展示 split 和作业归属
- `zoom-in` 时展示机器实时状态

同时定义每层级的:

- 必显信息
- 可选信息
- 必须隐藏的信息

这样后面不论换视觉稿还是组件实现，团队都不会把地图做成“所有信息同时堆上去”的样子。

### 建议 4: 给 `MachineDashboard` 增加调度视角

建议增加筛选:

- 仅看忙碌
- 仅看异常
- 仅看未确认
- 按机器类型筛选

否则机器一多就会变成纯浏览页。

### 建议 5: `JobListView` 增加优先级信息

当前表格适合历史记录，但不适合运营盯盘。

建议增加:

- 运行中作业置顶
- 失败作业高亮
- 草稿/待下发/运行中分组

### 建议 6: 设置页降权或扩容

如果近期不打算把设置页做强，建议在主导航里降低存在感。

如果准备继续发展，建议把它扩展为:

- 系统参数
- 机器模板
- 默认参考点
- 任务模板
- 告警与通知

---

## 最终建议

一句话总结:

这版设计“能用，而且方向对”，但目前更像一个农业业务后台，还不是一个成熟的农场作业指挥界面。

如果你的目标是做出类似“模拟农场式”的管理体验，我建议继续坚持以下三件事:

- 让地图成为真正的主舞台
- 让首页先回答“现在农场发生了什么”
- 让作业、机器、地块三者形成强联动

这样后续无论换哪种视觉风格，产品都会是对的。
